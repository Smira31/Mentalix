# Mentalix — краткая операционная карта

> **Начинайте отсюда.** Этот файл — единая точка входа для владельца, Manus, Claude Code, Codex, GitHub Copilot и других агентов. Он отвечает на вопрос «что открыть дальше», но не заменяет продуктовые, технические или проверочные источники.

Mentalix — Telegram Mini App с фронтендом React/Vite/Tailwind в этом репозитории и отдельным приватным backend-репозиторием. Фронтенд размещается на Vercel; production API направляется на backend через `/api`. Нельзя предполагать устройство backend, состояние данных или контракт API, если они не подтверждены отдельно.

## Минимальный контекст для ИИ

Агент не должен читать весь репозиторий или все Markdown-файлы «на всякий случай». Перед работой он загружает `AGENTS.md`, этот brief и **только один профильный источник**, который соответствует цели. Для реализации он дополнительно читает целевые файлы кода и Issue/PR. `PROJECT_STATE.md` обязателен только для работ, затрагивающих product scope, release, infrastructure, data, backend/API или production.

| Роль         | Минимальный набор                                                                | Результат роли                                             |
| ------------ | -------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Координатор  | `AGENTS.md`, этот brief, `PROJECT_STATE.md`, `docs/TASK_INDEX.md`, свежий GitHub | Короткий статус, риски, один следующий decision gate.      |
| Исполнитель  | `AGENTS.md`, этот brief, Issue/PR, целевые файлы и один профильный документ      | Один малый scope, одна ветка, один PR.                     |
| Ревьюер / QA | `AGENTS.md`, этот brief, diff PR, необходимые проверки                           | Список blocker/major/minor и честные ограничения проверки. |

**Один диалог — одна роль.** Координатор не меняет код, ревьюер не «доправляет заодно», а исполнитель не начинает вторую задачу до завершения первой. Одновременно только один writer меняет канонические документы или один и тот же набор файлов.

## Единый рабочий цикл

Работа движется по одной простой цепочке: **Issue → Ready → одна feature-ветка → Pull Request → checks → ручной gate, если требуется → merge → verified**. Issue описывает проблему и критерий результата; PR содержит маленький diff, доказательства и rollback. GitHub ruleset защищает `main` через PR; дополнительные обязательные checks могут быть включены в ruleset после их стабилизации.[1]

| Стадия     | Владелец                                                               | Агент                                         | Артефакт                         |
| ---------- | ---------------------------------------------------------------------- | --------------------------------------------- | -------------------------------- |
| Выбор      | Формулирует желаемый результат и приоритет                             | Уточняет scope, риски и ограничения           | Issue или запись в `TASK_INDEX`  |
| Реализация | Подтверждает границы для чувствительных изменений                      | Работает в отдельной ветке без лишних правок  | Небольшой diff                   |
| Проверка   | Проходит ручной Telegram/device gate, если он обязателен               | Запускает релевантные автоматические проверки | Evidence в PR                    |
| Решение    | Одобряет merge, если задача влияет на продукт, данные, API или release | Не выполняет merge без отдельного разрешения  | PR и merge commit                |
| Память     | Смотрит актуальный status/roadmap                                      | Обновляет только нужный источник истины       | `PROJECT_STATE` или `TASK_INDEX` |

Для задач, которые появляются часто, используйте существующие шаблоны Issues. GitHub поддерживает формы и шаблоны с обязательными полями, метками и маршрутизацией; это полезнее, чем создавать новые параллельные списки дел.[2]

## Владение документацией

> **Одна документация не означает один огромный файл.** Она означает один источник истины для каждого вопроса и отсутствие копирования одного и того же статуса в нескольких местах.

| Документ                                                    | Единственное назначение                               | Когда обновлять                                                    | Читать по умолчанию           |
| ----------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------- |
| `PROJECT_BRIEF.md`                                          | Старт, маршрутизация, правила экономии контекста      | При изменении рабочего процесса                                    | Да                            |
| `AGENTS.md`                                                 | Короткие обязательные правила для всех ИИ             | При изменении границ/процесса                                      | Да                            |
| `PROJECT_STATE.md`                                          | Подтверждённый current/release snapshot               | После проверенного merge, release, инцидента или решения владельца | Только для существенных работ |
| `docs/TASK_INDEX.md`                                        | Только активные задачи, статус и следующий gate       | При изменении статуса активной задачи                              | При планировании              |
| GitHub Issue и PR                                           | Scope, обсуждение, evidence и решение по одной работе | В ходе соответствующей задачи                                      | Для конкретной задачи         |
| `PRODUCT.md`, `ARCHITECTURE.md`, `DESIGN_SYSTEM.md`         | Нормативы продукта, техники и UI                      | Только при осознанной смене соответствующего решения               | Только профильный             |
| `TASKS.md`, `CHANGES.md`, `docs/archive/`, `docs/handoffs/` | История и архивная детализация                        | Не использовать для нового текущего статуса                        | Нет                           |

Если источники расходятся, не угадывайте. Зафиксируйте расхождение в Issue или PR, укажите ссылки и попросите решение владельца. GitHub и факт кода/проверки имеют приоритет над старым handoff; недоказанный production status не подменяется зелёной сборкой.

## Экономия времени и токенов

Каждый новый запрос должен содержать одну роль, одну цель, ссылку на Issue/PR или task ID и явные границы. Не вставляйте в чат полные исторические документы: передавайте ссылку и спрашивайте ровно тот раздел, который нужен. Просите агента сначала выдать read-only status, затронутые файлы, проверку и rollback в 8–12 строках; только затем подтверждайте реализацию.

Для сложной работы полезно разделять модели по роли, а не заставлять одну модель делать всё сразу. Один агент координирует и уточняет scope, один реализует в ветке, а другой проводит независимый review. Любая модель обязана соблюдать `AGENTS.md`; менять канонические документы и один набор файлов параллельно нельзя. После завершения одного PR начинайте чистый чат с кратким handoff, а не продолжайте длинную смешанную историю.

## Готовый запрос для нового диалога

```text
Mentalix / роль: [координатор | исполнитель | QA]
Цель: [одна наблюдаемая цель]
Issue или PR: [ссылка / ID]
Не менять: backend, API, данные, secrets, production и product scope без моего отдельного решения.

Сначала прочитай AGENTS.md, PROJECT_BRIEF.md, связанный Issue/PR и [один профильный документ].
Затем покажи: свежий read-only status, точный scope, затрагиваемые файлы, проверки, риски и rollback.
Не делай commit, push, merge, deploy, rebase, удаление или внешнюю публикацию без моего отдельного подтверждения.
```
