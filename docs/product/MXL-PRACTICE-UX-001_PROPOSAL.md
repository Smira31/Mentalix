# MXL-PRACTICE-UX-001 — unified problem-led practices

**Статус:** UX/content proposal, код не изменяет.  
**Issue:** [#296](https://github.com/Smira31/Mentalix/issues/296)  
**Дата:** 28 августа 2026 года  
**Объём:** «Первый шаг», «Без вины», «Одно из всех», «Один финиш»  
**Автор:** Manus AI

## 1. Решение в одном абзаце

Четыре психологические практики следует привести к одному понятному пользовательскому контракту: **problem framing → 2–4 коротких шага → measurable next action → completion → возврат в Today**. Практика не должна выглядеть самостоятельным мини-курсом или каталогом техник. Её задача — помочь человеку распознать конкретное затруднение, сделать одну небольшую проверяемую вещь и вернуться в главный ежедневный цикл Mentalix.

Это предложение развивает action-first позиционирование Mentalix: пользователь приходит не за количеством упражнений, а за переходом от состояния и понимания к следующему реальному шагу [1]. Конкурентные продукты используются как источник поведенческих принципов, но тексты, названия, бренд и UI Stoic не копируются [2].

> Практика считается полезной не тогда, когда пользователь дошёл до красивого success-state, а тогда, когда он понял проблему, выбрал один проверяемый шаг и может продолжить ежедневный цикл.

## 2. Текущая база и разрыв

В `src/screens/Practices.jsx` четыре практики уже собраны в категории «Психологические практики» и названы через пользовательскую ситуацию: «трудно начать», «откладываешь», «всё сразу», «один финиш». Это правильная информационная архитектура: пользователь выбирает не абстрактную технику, а ответ на узнаваемую проблему.

Текущие flow уже содержат сильные элементы, но они не оформлены единым контрактом. «Первый шаг» имеет problem framing, timed action, outcome и recovery для усталости; «Без вины» добавляет снятие самонаказания и двухминутный re-entry; «Одно из всех» использует mental dump → narrowing → action; «Один финиш» правильно уменьшает незавершённый проект до маленького куска. При этом все flow в разной форме содержат шесть шагов, сохраняют в основном `outcome` и `reflection`, используют общий финальный CTA «Завершить» и закрываются обратно в Practices через `onClose`.

Основной разрыв — отсутствие явного результата, который переносится в Today. Пользователь может пройти упражнение, но не понять, какое конкретное действие создано, где оно находится и как вернуться к ежедневному циклу. Именно поэтому proposal не предлагает добавлять новые психологические техники: сначала нужно унифицировать существующие четыре и сделать их проверяемыми [3].

| Сейчас                                                 | Предлагаемый контракт                                    |
| ------------------------------------------------------ | -------------------------------------------------------- |
| 5–6 шагов, различная логика экранов                    | 2–4 смысловых шага после framing                         |
| Generic «Завершить»                                    | CTA, называющий результат сессии                         |
| `outcome`/`reflection` без явного next action          | Одно измеримое действие с условием проверки              |
| `onClose()` возвращает в Practices                     | Завершение возвращает в Today и показывает созданный шаг |
| Recovery разный и иногда не связан с результатом       | Единый мягкий exit/recovery contract                     |
| Психологические формулировки могут звучать как диагноз | Наблюдаемая бытовая проблема, без medical claims         |

## 3. Единый session template

### 3.1. Problem framing

Каждая практика начинается с короткого экрана, который называет наблюдаемую ситуацию и обещает результат **одной сессии**. Framing не должен диагностировать человека, объяснять его личность или обещать лечение. Формула:

> «Если сейчас [наблюдаемая трудность], эта короткая практика поможет [ограниченный результат], чтобы ты мог [один следующий шаг]».

Нужно показывать ориентировочное время и количество шагов, но не создавать впечатление обязательного курса. Кнопка входа должна называться по ожидаемому действию, например «Выбрать один шаг» или «Освободить два минуты», а не только «Начать».

### 3.2. Два–четыре коротких шага

Шаги должны быть смысловыми, а не дроблением каждого поля на отдельный экран. У каждого шага есть один вопрос, короткий пример ответа и понятный переход. Нельзя требовать длинного письма там, где задача — начать действие. Разрешён выход без чувства провала; незаполненный optional reflection не должен блокировать завершение.

Рекомендуемый каркас:

1. назвать конкретную ситуацию;
2. выбрать или сформулировать ближайший фрагмент, которым можно управлять;
3. сделать короткое действие или заключить ограниченный re-entry contract;
4. зафиксировать измеримый next action.

Таймер допустим только как средство ограничить объём, а не как соревнование. «Пять минут» означает «достаточно для первой проверки», а не обязательство закончить всю задачу.

### 3.3. Measurable next action

Next action должен быть наблюдаемым и ограниченным. Он отвечает на четыре вопроса: **что** сделать, **в каком объёме**, **когда или при каком триггере**, **как понять, что действие выполнено**. Формат для UI/content:

> «Сегодня до [времени/события] я [глагол + конкретный объект] в объёме [малый измеримый результат]. Проверка: [наблюдаемый признак].»

Если время неизвестно, можно использовать контекстный триггер: «после обеда», «перед первым звонком», «когда открою документ». Не использовать «поработать над», «заняться», «попробовать» без объекта и признака завершения.

### 3.4. Completion

Completion подтверждает не личную «победу», а выполненную работу сессии. Экран должен показывать: что пользователь заметил, какое действие выбрал и какой следующий шаг создан. Разрешённые исходы должны быть честными:

| Outcome     | Значение                                                   |
| ----------- | ---------------------------------------------------------- |
| `started`   | действие начато, но не завершено целиком                   |
| `completed` | выбранный малый объём выполнен                             |
| `planned`   | следующий шаг сформулирован, но действие ещё не начато     |
| `stopped`   | пользователь остановился или вышел без вреда для состояния |

`stopped` не должен называться «провалом». Для него нужен нейтральный путь повторного входа или возврата в Today без давления.

### 3.5. Возврат в Today

Основной финальный CTA должен вести в Today и сообщать, что произойдёт: **«Вернуться в Сегодня»** или **«Продолжить в Сегодня»**. Вторичный CTA может открыть созданный next action, если такой объект уже существует. Возврат не должен вести в Practices по умолчанию: это разрывает daily loop и оставляет пользователя в каталоге.

На Today должна быть видна связь с результатом практики только после подтверждения фактического persistence-контракта. Если на текущем этапе запись сохраняется локально, текст должен честно обозначать локальное состояние и не обещать синхронизацию, историю или напоминание, которые ещё не реализованы.

## 4. Content proposal по практикам

### 4.1. «Первый шаг»

**Пользовательская проблема.** Задача кажется слишком большой, старт вызывает трение, и человек заменяет начало подготовкой, планированием или откладыванием. Это описание ситуации, а не диагноз «ленивый» или «немотивированный».

**Обещанный результат одной сессии.** Пользователь уменьшает задачу до первого физически выполнимого действия и либо делает его в коротком окне, либо получает честный re-entry plan.

**Proposed framing.** «Трудно начать? Не нужно решать всю задачу. За несколько минут найдём первый шаг, который можно проверить прямо сегодня.»

**Шаги.**

1. **Назвать задачу.** «Что ты откладываешь или не можешь начать?» Пример: «открыть документ и собрать три источника».
2. **Уменьшить вход.** «Что можно сделать за пять минут, не готовя всю работу?» В ответе должен быть один глагол и объект.
3. **Сделать короткий старт.** Запустить ограниченное окно и выполнить только выбранный первый фрагмент. CTA: **«Начать первый шаг»**.
4. **Зафиксировать продолжение.** Если старт сделан, сформулировать следующий маленький объём; если не сделан, сохранить причину без стыда и предложить re-entry.

**Measurable next action.** «Сегодня до [триггера] я [открою/напишу/соберу] [конкретный фрагмент] за [лимит]. Готово, когда [наблюдаемый признак]». Пример: «После обеда открою документ и напишу первые три пункта. Готово, когда три пункта будут на странице.»

**CTA.** Вход: «Найти первый шаг». Запуск: «Начать первый шаг». Финал: «Продолжить в Сегодня».

**Completion criterion.** Практика завершена, если зафиксирован конкретный первый шаг и выбран один из честных исходов: старт выполнен, старт начат или сформирован re-entry plan. Общая задача не обязана быть закончена.

**Recovery-сценарии.** Если пользователь устал или сопротивление ощущается слишком сильным, не убеждать его продолжать. Показать «Не сейчас — и это нормально» и дать три равноправных варианта: «Сделать шаг ещё меньше», «Записать, с чего начать позже» и «Выйти без результата». Мягкие формулировки: «Похоже, сейчас даже маленький старт требует слишком много сил. Можно остановиться»; «Не нужно доказывать, что ты можешь. Давай оставим только один возможный вход на потом»; «Если сегодня не время, это не делает задачу хуже и не говорит ничего о тебе».

Если пользователь вышел во время таймера, сохранить только локальный draft/session state согласно существующему persistence-контракту; не выдавать это за completion. Текст выхода: «Ты остановился на этом шаге. Ничего не потеряно — можно вернуться позже или оставить задачу до завтра». Если задача сформулирована слишком широко, не требовать новой формулировки сразу: «Можно не выбирать весь план. Назови только то, что будет видно после первых двух минут».

**Safety/content risks.** Не использовать «просто возьми себя в руки», «ты саботируешь» и обещания победить прокрастинацию. Сильное сопротивление не следует трактовать как лень или доказательство скрытой причины. Не предлагать действие, которое может быть физически опасным, нарушать чужие права или требовать профессионального решения. При упоминании кризиса, самоповреждения, насилия или острой опасности практика должна остановиться: «Я не буду вести тебя через упражнение, когда нужна более непосредственная поддержка. Пожалуйста, обратись к человеку или службе, которые могут быть рядом сейчас». Точный safety routing не является частью текущего кодового scope и должен быть согласован до production content.

### 4.2. «Без вины»

**Пользовательская проблема.** Человек избегает действия и одновременно усиливает трение самокритикой: «я опять всё испортил», «уже поздно начинать». Важна не борьба с эмоцией, а снятие лишнего наказания, чтобы вернуть ограниченную способность действовать.

**Обещанный результат одной сессии.** Пользователь отделяет факт от самонаказания и выбирает двухминутный вход в действие без обещания исправить всё сразу.

**Proposed framing.** «Откладываешь и ругаешь себя? На этой сессии не нужно оправдываться. Мы отделим факт от вины и найдём две минуты, в которые можно вернуться.»

**Шаги.**

1. **Назвать действие и факт.** «К чему ты сейчас не возвращаешься?» и «Что произошло фактически, без оценки себя?»
2. **Освободить место для старта.** «Что мешает вернуться сейчас?» Выбрать одно трение: усталость, страх оценки, неясность, отвлечение или слишком большой объём.
3. **Заключить re-entry contract.** «Я возвращаюсь к [объекту] на две минуты и делаю [один фрагмент]. После этого могу остановиться.» CTA: **«Вернуться на две минуты»**.
4. **Сформулировать продолжение.** Зафиксировать, что сделано или где остановиться в следующий раз.

**Measurable next action.** «Когда [триггер], я вернусь к [объекту] на две минуты и сделаю [один наблюдаемый фрагмент]. Готово, когда [признак].» Пример: «После чая открою письмо и напишу только тему и первое предложение.»

**CTA.** Вход: «Снять лишнее давление». Действие: «Вернуться на две минуты». Финал: «Продолжить в Сегодня».

**Completion criterion.** Есть нейтрально названный факт, выбран один источник трения и сформирован или выполнен двухминутный re-entry. Пользователь не обязан почувствовать себя лучше и не обязан закрыть исходную задачу полностью.

**Recovery-сценарии.** Если самокритика усиливается или пользователь отвечает «не знаю», пропустить reframe и не заставлять искать правильное объяснение. Мягкие формулировки: «Можно пока ничего не объяснять. Достаточно заметить: сейчас возвращаться трудно»; «Тебе не нужно заслуживать право на паузу»; «Мы можем не решать это сегодня — оставим только один безопасный способ вернуться, если захочешь».

Если две минуты оказались слишком тяжёлыми, уменьшить их до одного действия без таймера: «Открой файл, посмотри на первый экран и реши, продолжать ли. На этом можно закончить». Если пользователь прекращает сессию, финал: «Ты остановился. Это не провал и не обещание, что нужно вернуться. Можно сохранить следующий вход или просто закрыть практику» и CTA «Сохранить следующий вход».

**Safety/content risks.** Не говорить, что вина всегда бесполезна, и не обесценивать последствия реального вреда. Нельзя превращать практику в моральное оправдание нарушения обязательств. Не использовать терапевтические или медицинские обещания, не утверждать, что упражнение заменяет психотерапию. При сильном эмоциональном ответе использовать: «Похоже, сейчас важнее не заставлять себя действовать. Давай остановимся»; «Я не буду спорить с тем, что произошло. Можно выбрать паузу и обратиться за поддержкой». Если пользователь пишет о насилии, угрозе, зависимости или самоповреждении, не продолжать обычный guilt-release script без отдельного safety flow.

### 4.3. «Одно из всех»

**Пользовательская проблема.** Одновременно открыто слишком много задач, поэтому выбор становится отдельной задачей, а внимание распределяется между всеми направлениями. Mental dump уже присутствует в текущем flow; его нужно сохранить, но не превращать в длинный журнал.

**Обещанный результат одной сессии.** Пользователь выгружает нагрузку, выбирает один предмет внимания на сейчас и превращает его в небольшой проверяемый шаг; остальное временно получает статус «не сейчас».

**Proposed framing.** «Всё навалилось одновременно? Мы не будем решать весь список. Выгрузим его и выберем только одно, с чем можно начать сегодня.»

**Шаги.**

1. **Выгрузить список.** Записать всё, что занимает голову, короткими строками без попытки сразу решить.
2. **Выбрать одно.** «Что сильнее всего изменит ближайшие часы или снимет главное трение?» Выбор должен быть добровольным; остальные пункты не удаляются.
3. **Сузить до действия.** «Какой фрагмент этого одного пункта можно увидеть готовым через пять минут?» CTA: **«Выбрать один шаг»**.
4. **Зафиксировать остальное.** Next action для выбранного пункта и нейтральная отметка, что остальные пункты отложены, а не провалены.

**Measurable next action.** «Сегодня я начну с [одного объекта] и выполню [малый объём] до [триггер/время]. Готово, когда [наблюдаемый признак].» Пример: «До первого звонка составлю список из трёх вопросов к встрече.»

**CTA.** Вход: «Освободить голову». Сужение: «Выбрать один шаг». Финал: «Продолжить в Сегодня».

**Completion criterion.** Внешний список выгружен или осознанно пропущен, выбран один объект, next action имеет объект и критерий готовности. Выполнение всего списка не является критерием.

**Recovery-сценарии.** Если список бесконечный или пользователь застывает перед пустым полем, не требовать полного mental dump. Предложить: «Можно написать только три вещи, которые сейчас громче всего. Остальное не нужно удерживать здесь»; «Если даже три пункта — много, напиши один или выбери “не сейчас”». Ограничить выгрузку двумя минутами или десятью строками и предложить продолжить позже.

Если пользователь не может выбрать, использовать вопрос «что имеет ближайший реальный срок?» без автоматического выбора за него. При сильном сопротивлении: «Не обязательно выбирать самое важное на всю жизнь. Выбери то, к чему проще безопасно прикоснуться сегодня»; «Можно отложить выбор и сделать только список вариантов — решение останется за тобой». Если выбранный пункт оказался неуправляемым, сказать: «Это не в твоём полном контроле. Найдём только ту часть, которую можно подготовить или попросить».

**Safety/content risks.** Не обещать, что один шаг решит перегрузку. Не использовать «приоритеты» как скрытое требование продуктивности в ситуации истощения и не называть отложенные пункты неважными. Не собирать в mental dump лишние чувствительные данные и не отправлять его AI без отдельного consent. При сильном ответе «я не справляюсь» не отвечать списком задач: «Похоже, сейчас список — не то, что поможет. Можно остановиться и выбрать поддержку или паузу». Если в списке появляются симптомы острого кризиса, сначала нужен safety routing, а не оптимизация задач.

### 4.4. «Один финиш»

**Пользовательская проблема.** Человек застрял в незавершённом проекте: начало уже сделано, но масштаб оставшейся работы или страх плохого результата мешают закрыть конкретный кусок. Здесь цель — не «закончить всё», а вернуть ощущение завершения малого объёма.

**Обещанный результат одной сессии.** Пользователь выбирает один незавершённый проект, определяет минимальный кусок, который можно закрыть сегодня, и формулирует проверяемое условие финиша.

**Proposed framing.** «Застрял на незавершённом? Не нужно закрывать весь проект. Найдём один маленький кусок, который можно довести до финиша сегодня.»

**Шаги.**

1. **Назвать проект.** «Что осталось незавершённым?» Нужен один проект, а не весь backlog.
2. **Назвать место остановки.** «На чём застряло?» Выбрать одно: неясный следующий шаг, слишком большой объём, ожидание идеала, усталость или внешняя зависимость.
3. **Определить малый финиш.** «Какой кусок можно считать законченным отдельно от всего проекта?» CTA: **«Выбрать один финиш»**.
4. **Зафиксировать проверку.** Указать, что будет считаться завершённым и что останется за пределами этой сессии.

**Measurable next action.** «До [триггер/время] я завершу [малый кусок] в [объём]. Финиш наступил, когда [наблюдаемый признак].» Пример: «До ужина отредактирую один абзац и отправлю его на проверку; финиш — письмо отправлено.»

**CTA.** Вход: «Найти один финиш». Действие: «Начать этот кусок». Финал: «Продолжить в Сегодня».

**Completion criterion.** Определён отдельный кусок, который можно проверить без завершения всего проекта, и зафиксирован исход: кусок закрыт, начат или назначен к возврату. Не считать completion по исчезновению проекта из списка.

**Recovery-сценарии.** Если кусок нельзя отделить, уменьшить его до артефакта: черновик, один абзац, один тест или один отправленный вопрос. Мягкая формулировка: «Похоже, этот кусок пока нельзя честно назвать отдельным финишем. Можно выбрать только подготовку к нему»; «Финиш не обязан быть большим. Достаточно сделать один предмет, который можно увидеть готовым».

Если финиш зависит от другого человека, next action должен быть собственным действием пользователя: отправить запрос, подготовить материалы или назначить follow-up. При сопротивлении: «Не нужно закрывать зависимость в одиночку. Давай зафиксируем один вопрос или сообщение, после которого следующий шаг будет у другой стороны». Если пользователь остановился из-за усталости: «Сегодня можно закончить не работу, а решение о границе: что мы точно не делаем сегодня». CTA: «Сохранить границу и вернуться в Сегодня».

**Safety/content risks.** Не подталкивать завершать действие, если зависимость, безопасность или согласие другого человека не подтверждены. Если пользователь говорит «я должен закончить любой ценой», ответ должен снижать давление: «Нет необходимости доводить это до конца прямо сейчас. Сначала проверим, безопасно ли продолжать и нужен ли кто-то ещё». Не романтизировать переработку и не связывать ценность человека с продуктивностью. Формулировка «финиш» должна быть локальной и операциональной, а не обещать закрытие эмоционально тяжёлой ситуации.

## 5. Общие content rules

| Правило              | Применение                                                                        |
| -------------------- | --------------------------------------------------------------------------------- |
| Наблюдаемая проблема | Описывать ситуацию и действие, не черту личности и не диагноз                     |
| Один результат       | Каждая сессия создаёт один measurable next action                                 |
| Малый объём          | Указывать объект, лимит и признак готовности                                      |
| Спокойный тон        | «На ты», коротко, без стыда, давления и мотивационного шума                       |
| Честный статус       | Не называть план выполнением и не обещать backend/history до контракта            |
| Safety boundary      | Не лечить, не диагностировать, не обещать изменение психического состояния        |
| Добровольный выход   | Выход и остановка не маркируются провалом                                         |
| AI boundary          | Не подключать AI к пользовательскому тексту без отдельного consent и data preview |
| No catalogue creep   | Не добавлять новые problem tracks в этот scope                                    |

## 6. Acceptance criteria для будущей реализации

Будущий кодовый PR может считаться соответствующим этому proposal, если:

1. Все четыре flow используют один и тот же смысловой порядок: framing, 2–4 коротких шага, action, completion, return.
2. У каждой практики есть собственный problem framing, одно обещание результата сессии и собственный measurable next action.
3. CTA в каждом flow описывает действие пользователя, а финальный CTA ведёт в Today.
4. Completion различает выполнение, начало, план и остановку; generic success без результата не считается достаточным.
5. В UI видны объект next action и критерий готовности, если persistence-контракт это поддерживает.
6. Recovery-сценарий позволяет уменьшить шаг, отложить возврат или безопасно выйти без language of failure.
7. Текущая local-first/persistence семантика не расширяется по предположению; не заявляются sync, history, reminders или AI handoff без подтверждённого контракта.
8. Не меняются Today, CheckIn, Journal persistence/history/privacy, App, Series & Badges и навигационная модель.
9. Проходят `npm run check:core`, целевые UX smoke checks и предусмотренный Telegram/iPhone manual gate.
