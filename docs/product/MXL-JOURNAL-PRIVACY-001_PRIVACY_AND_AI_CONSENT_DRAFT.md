# MXL-JOURNAL-PRIVACY-001 — черновик privacy и AI consent

> **Рабочий draft — не юридическая консультация и не готовая privacy policy.** Перед production-релизом документ должен проверить квалифицированный юрист с учётом юрисдикций, Telegram Mini Apps, фактического backend и используемых AI-провайдеров.

**Статус:** product/safety/backend draft. Не разрешает подключать новые endpoint, telemetry или AI-передачу без отдельной проверки.

## 1. Базовые принципы

Mentalix должен считать journal entry личным содержимым пользователя, а не обычным продуктовым событием. По умолчанию свободная запись сохраняется локально в пределах согласованного storage contract и не отправляется в AI, backend, analytics или Telegram-сообщения без отдельного действия пользователя. Интерфейс не должен создавать впечатление, что локальная запись синхронизирована с облаком, если это не подтверждено сервером.

Ключевые принципы: **минимизация данных**, **ясная цель**, **явное действие**, **обратимость**, **видимый статус хранения**, **разделение journal content и telemetry**, **безопасная деградация** при ошибке и **отсутствие медицинских обещаний**.

## 2. Классы данных

| Класс | Примеры | Default handling | Нужен отдельный consent |
|---|---|---|---|
| Journal content | Идея, действие, анализ, новый шаг, free write | Локальное сохранение как draft/final | Да, перед передачей в AI или cloud sync |
| Check-in | mood, energy, focus, emotion, note, lessons, wins | Используется только в заявленном продуктом сценарии | Да, если добавляется новая цель обработки |
| Account identity | Telegram user identity, signed initData, internal user id | Только для авторизации и ownership | Не отдельный для базовой работы, но нужен notice |
| Technical data | app version, errors, device/viewport metadata | Минимально необходимое, без текста записей | Желателен opt-out/настройка для non-essential telemetry |
| AI request data | Выбранный фрагмент записи, persona, prompt context | Отправляется только после явного AI action | **Всегда явное согласие/подтверждение** |
| Attachments | Фото, видео, аудио | Не включать до отдельного privacy/storage contract | Да |

## 3. Draft пользовательских правил

1. Пользователь владеет содержимым своих записей. Mentalix не должен использовать journal content для рекламы, публичной публикации, обучения моделей или передачи третьим лицам без отдельного, конкретного и отзывного основания.
2. Запись, сохранённая как draft, не считается завершённой мыслью и не должна автоматически попадать в AI, insights, reminders или product analytics.
3. `final` означает только состояние дневникового цикла в приложении; это не должно трактоваться как медицинский, психологический или объективно правильный вывод.
4. Системные логи, crash reports и analytics не должны содержать полный текст записи, user-entered prompt, access token или raw Telegram initData.
5. В каждой поверхности должен быть понятен статус: «сохранено на устройстве», «синхронизировано», «ожидает синхронизации» или «не сохранено из-за ошибки». Нельзя показывать «сохранено» для неподтверждённой cloud operation.
6. Пользователь должен иметь возможность просмотреть активные настройки consent, отозвать необязательное согласие и понять последствие отзыва.

## 4. AI consent flow

AI-deepen — отдельное действие, а не побочный эффект сохранения. Перед первой отправкой нужно показать короткое объяснение рядом с CTA, а не прятать его только в длинной политике:

> «Чтобы наставник помог разобрать этот текст, выбранный фрагмент будет отправлен AI-провайдеру через Mentalix. Это необязательно: запись можно сохранить без AI. Проверь, нет ли здесь данных, которыми ты не хочешь делиться.»

Перед подтверждением пользователь должен видеть: какой текст отправляется, какая persona/функция его получит, цель обработки, кто является провайдером, возможный срок хранения по фактическому договору, отключена ли обработка для обучения, и что произойдёт при отказе. Согласие должно быть привязано к конкретному действию и версии disclosure, а не к общей галочке «согласен со всем».

Рекомендуемая модель состояний: `not_shown → disclosure_shown → accepted_once → declined → revoked`. `accepted_once` не означает бессрочное разрешение на любые будущие записи: для чувствительного текста нужен повторный понятный action или настройка, явно описывающая scope согласия.

Отзыв согласия должен останавливать новые AI-запросы, но не обещать удаление уже переданных данных, если фактический provider contract не даёт такого механизма. Интерфейс обязан честно объяснить это ограничение и показать путь удаления там, где он реально доступен.

## 5. Что нельзя делать автоматически

Нельзя отправлять в AI весь дневник при открытии Journal Home, строить персонализированный insight из текста без notice, использовать journal content для telemetry, silently sync draft, включать reminders на основе содержания записи, добавлять media upload, экспортировать в Telegram chat или считать AI-ответ терапевтической рекомендацией.

Нельзя обещать «полную приватность», «нулевое хранение», «end-to-end encryption», «не видит никто» или конкретный retention period до проверки фактического backend/provider contract. Нельзя автоматически определять кризис, диагноз или причину состояния по дневнику.

## 6. Retention, export и delete — draft policy

Фактические сроки нужно зафиксировать только после инвентаризации Neon, Render/backend logs, Vercel logs, Telegram delivery и AI provider. До этого безопасный product default: локальные drafts живут до удаления пользователем или очистки storage браузера; cloud entries — до явного удаления по подтверждённому backend contract; AI request/response — по минимальному сроку, который допускает provider contract, с публичным указанием фактического срока.

Export должен включать только данные пользователя в машиночитаемом формате и отдельно указывать источник и статус каждой записи. Delete должен иметь preview scope: какие local, cloud, cached и provider-side данные реально удалятся, какие могут остаться по legal/security retention, и как пользователь увидит результат. Не считать удаление UI-строки доказательством удаления из backend или AI provider.

## 7. Минимальная модель consent audit

Если backend позже поддержит consent ledger, концептуально необходимы: `user_id`/ownership, consent type, disclosure version, scope, timestamp, source surface, accepted/declined/revoked status и policy version. Полный journal text в consent ledger не хранить. Это только кандидат на контракт; названия таблиц и endpoint нельзя фиксировать до backend review.

## 8. Safety и чувствительные записи

Mentalix — инструмент рефлексии, а не врач, психотерапевт или кризисная служба. Копирайт должен избегать диагностики, причинных утверждений, давления и обещаний эффективности. Если пользователь вводит чувствительные сведения, UI не должен усиливать их распространение: AI disclosure должен быть видимым, а free write — полноценным режимом без AI.

Возрастной режим, crisis handling, legal basis, controller/processor roles, international transfer и provider agreements остаются открытыми safety/legal gates. Этот draft не заменяет их решение.

## 9. Definition of Done

Privacy-задача готова только после инвентаризации всех мест хранения и передачи, подтверждённого backend и AI provider contract, финального текста disclosure, настройки consent/revocation, реального export/delete сценария, отсутствия journal content в telemetry, unit/integration/UX проверок и ручного Telegram/iPhone gate. До этого `MXL-JOURNAL-PRIVACY-001` остаётся draft/needs-owner.

## 10. Открытые решения владельца

| Вопрос | Почему блокирует реализацию |
|---|---|
| Cloud sync включён по умолчанию или opt-in? | Меняет consent, UX и storage contract |
| AI consent одноразовый, на сессию или на каждую запись? | Определяет риск случайной передачи текста |
| Допустим ли provider-side retention и какой срок? | Нельзя написать честный disclosure без фактического договора |
| Нужны ли export и delete в первой cloud-версии? | Влияет на schema, UI и операционные процедуры |
| Какой возрастной/safety regime? | Меняет copy, onboarding и обработку чувствительных данных |
| Какие non-essential telemetry разрешены? | Определяет data minimization и opt-out |
