# Аудит визуального контракта полноэкранных flow-практик

**Статус:** diagnostic-only; runtime-код намеренно не изменялся.

**Репозиторий:** [Smira31/Mentalix](https://github.com/Smira31/Mentalix), `main` на момент аудита 2026-09-21.

**Цель:** подготовить безопасную унификацию полноэкранных практик по визуальному эталону «Без вины» (`ProcrastinationFlow`), не смешивая в один рефакторинг навигацию, ввод, progress UI и разные доменные state machine.

## Вывод

В проекте уже есть **частичный общий инфраструктурный контракт**, но нет одного переиспользуемого `FullscreenFlowShell`, который задаёт одновременно header, вертикальную композицию, keyboard-safe writing layout, CTA и completion feedback. Общие primitives — `useFullscreenSurface`, классы `FULLSCREEN_SHELL_CLASS` / `FULLSCREEN_SCROLL_CLASS`, `BackButton`, `WebActionBar`, а также `SceneLayout` — соседствуют с несколькими независимыми layout-системами.

Основная группа новых guided-практик (`FirstStepFlow`, `ProcrastinationFlow`, `NarrowFocusFlow`, `FinishFlow`) уже визуально близка между собой и использует `JournalTextarea` с `guidedFlow`; при этом каждая из трёх последних практик дублирует собственные `Stage`, `Progress`, artwork и completion CSS. `GuidedSelfDiscoveryFlow`, `JournalFlow` и `LilaDiscoverFlow` используют отдельные canvas/shell-контракты. `GuidedJournals` остаётся отдельным старым каталогом с ручной текстовой навигацией.

**Рекомендация:** не создавать сразу один универсальный компонент для всех flow. Начать пилот с общей оболочки только для группы `FirstStepFlow` + `ProcrastinationFlow` + `NarrowFocusFlow` + `FinishFlow`, сохранив domain-specific stage content и state machine. После визуальной проверки в Telegram вынести в shared contract: header slot, scroll surface, writing scene, CTA/action dock и completion layout. `GuidedSelfDiscoveryFlow` и `JournalFlow` подключать вторым этапом; `LilaDiscoverFlow` и `GuidedJournals` — отдельно из-за иной chat/catalog semantics.

## Методика и границы

Проверены production entry points из [`src/screens/Practices.jsx`](https://github.com/Smira31/Mentalix/blob/main/src/screens/Practices.jsx) и список доступности в [`src/config/practiceAvailability.js`](https://github.com/Smira31/Mentalix/blob/main/src/config/practiceAvailability.js). В основной таблице отмечены доступные практики и связанные fullscreen flows, явно указанные owner'ом или реально присутствующие в routing. UI-lab/preview-only эксперименты не включены.

Критерии:

1. **Контент/CTA:** строго центрированная композиция, верхнее смещение или смешанный layout.
2. **Назад/действие:** native Telegram BackButton через общий `BackButton`/`useBackButton`, web fallback этого компонента или ручная текстовая/иконная кнопка.
3. **Шаг-бар:** пользовательский индикатор вида `N из M`/rail или отсутствие видимого progress.
4. **Текстовый ввод:** новый canvas/guided keyboard-safe style (`JournalTextarea` с `guidedFlow` или `PracticeWritingCanvas`) либо старый form/catalog style.
5. **Финальная оценка:** есть ли feedback «да/нет/немного» и где он расположен относительно completion content.

> «Native» ниже означает именно Telegram BackButton в Telegram; вне Telegram общий компонент может показывать web fallback, что является ожидаемым поведением общего контракта.

## Найденные дополнительные несоответствия

### 1. Навигация назад не унифицирована в GuidedJournals

Это наиболее явная production-находка сверх исходного контекста. В `GuidedJournals` native `BackButton` используется в архивном viewer, но каталог, detail и active-session state всё ещё рисуют ручные `ArrowLeft`/текстовые кнопки. Это тот же класс проблемы, что owner отдельно отмечал для других вложенных fullscreen states, но исправление потребует аккуратного выбора поведения: каталог должен возвращать в Library, detail — в каталог, active session — сохранять draft и выходить.

Наблюдение согласуется с существующим [back-button audit](https://github.com/Smira31/Mentalix/blob/main/docs/audit/BACKBUTTON_AUDIT.md), где `GuidedJournals` уже отмечен как partial/native-back gap. В этот audit не вносилось исправлений.

### 2. Progress semantics разъезжаются

Четыре guided practice flow показывают progress rail (`1 из 5` или `1 из 6`), тогда как `GuidedSelfDiscoveryFlow` и `JournalFlow` имеют внутренний индекс steps/phases, но намеренно не показывают пользовательский step bar. `GuidedJournals` показывает только текст `N из M`. Это не обязательно баг: это разные information architectures, но при унификации нужно заранее выбрать, что именно является частью общего contract, а что — domain option.

### 3. Есть несколько независимых keyboard-safe реализаций

`JournalTextarea + guidedFlow` и `PracticeWritingCanvas` обе являются современными input primitives, однако их surrounding CSS различается. У `ProcrastinationFlow` дополнительно есть `useLayoutEffect` и явный scroll reset; у `GuidedSelfDiscoveryFlow`/`JournalFlow` dock реагирует на keyboard state; у Lila query используется собственный canvas class. При исправлении нельзя механически менять все поля на один компонент без проверки iOS Telegram WebView и переходов между каждым текстовым шагом.

### 4. Общий `BackButton` уже решает platform split, но не state semantics

`BackButton` корректно скрывается в Telegram и монтирует `useBackButton`; web fallback показывается вне Telegram. Однако компонент не знает, как менять локальный flow state. Поэтому наличие общего компонента в header ещё не доказывает, что back на каждом промежуточном шаге возвращает именно на предыдущий шаг: это нужно проверять в каждом state machine. Для `FirstStepFlow`, `GuidedSelfDiscoveryFlow`, `LilaDiscoverFlow`, `JournalFlow` такие локальные handlers явно есть; у `ProcrastinationFlow`, `NarrowFocusFlow`, `FinishFlow` header сейчас вызывает `onClose`, то есть back с промежуточного шага закрывает весь flow, а не возвращает предыдущий шаг.

## Что нельзя заключить из текущего кода без product decision

### Mood / energy scale и «фокус дня»

В production routing для перечисленных guided flows **нет отдельного mood scale, energy scale или шага «фокус дня»**. В `ProcrastinationFlow`, `NarrowFocusFlow`, `FinishFlow` и `FirstStepFlow` state machine содержит task/dump/project, choices, plan/run/outcome/reflection, но не mood/energy/focus-day state. `GuidedSelfDiscoveryFlow` содержит семь текстовых вопросов, включая «Что зависит от тебя сегодня?» и «Какой маленький эксперимент попробуешь?», но это не mood/energy scale и не отдельный «фокус дня» экран.

Это может быть намеренной упрощённой версией текущих практик, а может быть расхождением с video reference. **В рамках audit код не расширялся и новые шаги молча не добавлялись.** Нужен отдельный product decision: считать ли отсутствие mood/energy/focus-day ожидаемым сокращением или багом потери шагов при переключении flow.

## Рекомендованный план унификации

1. **Пилот: `FirstStepFlow` + `ProcrastinationFlow`.** Зафиксировать один mobile-height/keyboard matrix и сравнить intro, первый text step, choice, run и completion в Telegram iOS/Android. Не трогать state machine и сохранение данных.
2. Вынести минимальный `FullscreenPracticeShell` или набор composable primitives: header slot с `BackButton`, scroll region, `WritingScene`, `ChoiceScene`, `CompletionScene`, action dock. Не прятать в shell domain-specific progress/artwork.
3. В progress передавать явно опциональный `progress` slot. Это позволит не навязывать rail `GuidedSelfDiscoveryFlow` и `JournalFlow`, где внутренние steps существуют, но визуальный progress сейчас отсутствует.
4. Вынести keyboard-safe правила отдельно от typography: visual viewport/safe-area, focus scroll, dock placement, editor min-height. Проверить все поля каждой практики, а не только первый экран.
5. После пилота подключить `NarrowFocusFlow` и `FinishFlow`, затем `GuidedSelfDiscoveryFlow`/`JournalFlow`. `LilaDiscoverFlow`, `GuidedJournals`, `Breathing` и `BrainTrainer` оставить отдельными adapters/contracts.
6. Отдельным navigation PR исправить `GuidedJournals` ручные back controls и проверить semantics локальных back handlers у flows, где общий BackButton сейчас закрывает весь flow.

## Проверка

Аудит выполнен только чтением текущих source/styles/routing. Runtime-код не менялся, поэтому lint/build/unit-тесты для этого diagnostic-only PR не запускались как validation изменений поведения; следующий implementation PR должен обязательно прогнать `npm run lint`, `npm run build` и `npm run test:unit`, а также приложить Telegram screenshots для выбранного пилота.

## Итоговая рекомендация

Создание одного большого shared-компонента для всех перечисленных flow сейчас преждевременно: различия между guided practice, free-form journal, AI chat, guided-journal catalog и timed breathing exercise структурные, а не только визуальные. Оптимальный путь — **маленький composable shell для близкой группы четырёх guided practices**, с опциональными progress/art/completion slots, затем постепенное подключение остальных flow после Telegram QA. Отдельно требуется product-ответ по отсутствующим mood/energy scale и «фокусу дня».
