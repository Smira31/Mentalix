# Варианты тестового доступа для визуальных проверок prod

## Контекст

Два аудита подряд не смогли снять скриншоты каталога «Практики» / «Сегодня» на
`https://mentalix-production.web.app`: без авторизованной сессии виден только
guest/newsletter (email-capture), не основные вкладки.

**Не делается в этом документе:** создание реальных учёток, бэкдоров, ослабление
auth. История: `MXL-SECURITY-AUDIT-001`, риск захвата через незащищённый
`/link/generate`. Любой выбранный вариант — отдельное решение владельца с
оценкой поверхности атаки.

## Вариант 1 — выделенный Telegram QA-аккаунт + сессия, которую обновляет владелец

**Суть:** отдельный Telegram-аккаунт только для QA; владелец периодически
открывает Mini App, сохраняет storage/cookie (или Playwright `storageState`)
и передаёт агенту **out-of-band** (секрет-хранилище, не в git).

| Плюсы | Минусы |
| ----- | ------ |
| Близко к реальному Telegram UX | Cookie/session может утечь; нужен безопасный канал передачи |
| Не трогает backend contract | Сессия протухает; владелец должен обновлять |
| Не требует dev login endpoint | Агент с сессией = доступ к данным этого QA-аккаунта |

**Риски:** компрометация секрета = доступ к QA-профилю; не класть state в
репозиторий и CI logs.

## Вариант 2 — dev-only login endpoint за секретным ключом (не на prod-данных)

**Суть:** в **приватном** `mentalix-bot` endpoint вроде
`POST /api/qa/session` с заголовком `X-QA-Key`, возвращающий короткоживущий
token только для изолированного QA-пользователя / staging DB. Frontend
включает вход по токену только при `VITE_QA_LOGIN=1` и **не** на Firebase
Production origin.

| Плюсы | Минусы |
| ----- | ------ |
| Автоматизируемые скриншоты без Telegram cookie | Расширяет attack surface; нужен жёсткий scope |
| Можно запретить на production host | Требует backend-работы в private repo |
| Аудит и revoke ключа централизованы | Ошибка конфигурации → риск на prod |

**Риски:** ключ в CI/логах; обязательно origin allowlist, rate limit, отдельный
dataset, запрет на `mentalix-production.web.app`.

## Вариант 3 — не автоматизировать prod-данные; визуал = owner + локальный smoke

**Суть:** агент ограничивается `npm run ux:check` / UI Lab / Cloudflare Demo
Preview (exact-SHA). Скриншоты **production** с реальными данными — только
ручной gate владельца (Telegram/iPhone).

| Плюсы | Минусы |
| ----- | ------ |
| Нулевая новая поверхность атаки | Агент снова не снимет prod-скрин без владельца |
| Совпадает с текущей hosting policy | Медленнее закрывать UX-аудиты |
| Нет секретов сессии у агента | Зависимость от доступности владельца |

## Сравнение по критериям

| Критерий | V1 QA Telegram session | V2 dev login endpoint | V3 только manual + ux:check |
| -------- | ---------------------- | --------------------- | --------------------------- |
| Безопасность | Средняя (секрет сессии) | Зависит от реализации | Высокая |
| Близость к prod Telegram | Высокая | Средняя (web/token) | Высокая (owner) |
| Усилие на внедрение | Низкое/среднее | Высокое (backend) | Нулевое |
| Автономность агента | Средняя | Высокая (на QA env) | Низкая для prod |

## Рекомендация (не решение)

- Если приоритет — **безопасность и простота:** вариант **3** как норма;
  Demo Preview + owner gate для спорных экранов.
- Если нужны частые agent-скриншоты **без** prod-пользователей: **2** только на
  non-production origin + отдельный QA dataset.
- **1** — компромисс, если владелец готов сам ротировать session state и хранить
  его вне git.

**Финальный выбор и реализация — только после явного решения владельца.**
Этот PR ничего не внедряет.
