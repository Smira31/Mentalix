**Дата:** 28.08.2026, GMT+3.

> **Главный вывод:** описательные pattern insights в Mentalix — не гипотеза, а уже дважды реализованная и один раз formally closed фича (`MXL-009`, PR #221, ROADMAP «Дайджест от Следопыта»). ## 2. Существующий прототип: инвентарь (уже закрывает часть acceptance criteria)

Issue просит «прототип 2–3 типов descriptive observations». В коде их больше и они уже в проде на двух независимых поверхностях.

| Поверхность                               | Файл                                                           | Provenance                          | Показ                                                       |
| ----------------------------------------- | -------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------- |
| «Тренды» → «Наблюдения»                   | `Analytics.jsx`, `data.observations`/`data.insights` с backend | смешанный (см. §3)                  | карточки с caveat, sample size, датами-основанием           |
| Реплика «Следопыта» в диалоге с `dnevnik` | `insightDigest.js` → `deriveConclusions`                       | чисто клиентский, детерминированный | одно сообщение перед первым в диалоге, не чаще раза в 4 дня |

Шесть типов правил в `deriveConclusions` (`Analytics.jsx:390-495`), общие для обеих поверхностей:

| #   | Наблюдение                                | Сравнение                           | Guard                                       |
| --- | ----------------------------------------- | ----------------------------------- | ------------------------------------------- |
| 1   | Тревога vs завершённый вечерний разбор    | среднее по двум группам дней        | `MIN_GROUP=3` на группу, порог Δ≥0.6        |
| 2   | Настроение vs завершённый вечерний разбор | то же                               | `MIN_GROUP=3`, Δ≥0.5                        |
| 3   | Энергия vs собранность                    | группы energy≥4 / energy≤2          | `MIN_GROUP=3`, Δ≥0.7                        |
| 4   | Тренд настроения за период                | первая vs вторая половина           | `list.length ≥ MIN_CHECKINS*2` (≥10), Δ≥0.5 |
| 5   | День недели срывов аскез                  | доля срывов на самый частый weekday | `breakDays.length ≥ 3` и доля ≥50%          |
| 6   | Текущая серия закрытых дней               | streak counter                      | `streak ≥ 3`                                |

Формулировки уже наблюдательные, не причинные: «В этой выборке…», «чаще совпадало», «могли быть сложнее» — зафиксировано как продуктовое решение в `TASKS.md` (`MXL-009`). Это прямо отвечает на acceptance criterion «прототип 2–3 типов observations» — их фактически 6, задача не «создать», а **валидировать ценность уже существующего**.

## 3. Необходимые данные и provenance

### 3.1 Входные данные

| Поле                                           | Источник                  | Диапазон/тип после санитайзера                                                                                                                                 |
| ---------------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mood`/`energy`/`anxiety`/`focus`              | check-in                  | целое 1–5 или `null` (`scoreOrNull`, `trendsDataSanitizer.js:12-14`)                                                                                           |
| `review_completed_at`                          | check-in                  | строка или `null`, не валидируется дальше                                                                                                                      |
| `emotion`                                      | check-in                  | строка, обрезается                                                                                                                                             |
| `date`                                         | check-in / daily_activity | должен быть валидный `YYYY-MM-DD`; невалидные записи **отбрасываются целиком** (`validIsoDate`, `sanitizeCheckins`), дубликаты по дате — оставляется последняя |
| `rituals[].completion_rate`                    | backend                   | 0–100                                                                                                                                                          |
| `ascezas[].streak/clean_rate/held_days/breaks` | backend                   | ограничены 0–90                                                                                                                                                |
| `daily_activity[].breaks`                      | backend                   | 0–10000, используется для weekday-паттерна                                                                                                                     |
| `data.observations[]`                          | backend                   | `{kind, text, sampleSize, sourceDates, caveat}`, см. §3.2                                                                                                      |
| `data.insights[]`                              | backend (AI)              | до 3 строк, см. §3.2                                                                                                                                           |

### 3.2 Два разных provenance-канала — не одно и то же

Это ключевая находка для issue: в системе **два независимых источника** текста наблюдений с разным уровнем доверия, и UI между ними не объясняет разницу пользователю:

1. **`data.observations`** — структурированный контракт (`kind`, `text`, `sampleSize`, `sourceDates`, `caveat`). Судя по форме (совпадает 1:1 с тем, что производит клиентский `deriveConclusions`), это детерминированные правила, вероятно портированные на backend. Имеет приоритет в рендере (`Analytics.jsx:614-622`).
2. **`data.insights`** — массив свободного текста, по названию задачи `MXL-009` («Описательные AI-insights без причинных claims») это **LLM-сгенерированный** текст, отфильтрованный клиентским regex-фильтром `isDescriptiveInsight` (`descriptiveInsights.js`). Используется только если `data.observations` пуст.

UI не показывает пользователю, каким из двух способов получено конкретное наблюдение — обе ветки рендерятся в одинаковой карточке. Для issue это значит: «provenance» нельзя закрыть одной строкой «данные локальные» — нужно решить, раскрывать ли пользователю разницу между «посчитано по правилу» и «сформулировано моделью по тем же данным», и это открытый вопрос, не отвеченный в текущем коде.

### 3.3 Timezone / дата — открытый контрактный риск

`docs/architecture/MXL-JOURNAL-HISTORY-001_ARCHITECTURE.md` §7 прямо фиксирует нерешённый вопрос: группировка по calendar day должна идти по timezone-политике backend, а не по моменту рендера клиента, иначе запись «переезжает» в другой день при смене часового пояса пользователя. Наблюдение №5 (день недели срывов) целиком зависит от корректности этой группировки. Issue сам называет «корректную дату/timezone модель» зависимостью — на 28.08.2026 она **не закрыта** ни в этом репозитории, ни (насколько видно отсюда) в backend-контракте.

## 4. Sample-size guards

### 4.1 Что уже есть

- `MIN_GROUP = 3` — минимум валидных числовых значений на сравниваемую группу (`Analytics.jsx:338`), считается по числу непустых значений поля, а не по числу записей — так неполная запись не может искусственно раздуть выборку (см. комментарий в коде, `compareGroups`).
- `MIN_CHECKINS = 5` — минимум чек-инов для тренда (правило 4) и для показа реплики «Следопыта» вообще (`insightDigest.js:68`).
- `MIN_DAYS_BETWEEN_INSIGHTS = 4` — не sample-size guard, а частотный: не чаще одной реплики раз в 4 дня, независимо от объёма данных.
- Пороги минимальной разницы (Δ) на каждое правило — 0.5–0.7 по 5-балльной шкале, чтобы шум не читался как паттерн.
- `sanitizeObservations` (`trendsDataSanitizer.js:62-80`) ограничивает `sampleSize` диапазоном `[0, 10_000]` и обрезает список наблюдений до 3.

### 4.2 Найденный пробел

`sanitizeObservations` **не проверяет нижнюю границу** `sampleSize` содержательно — только клампит вверх/вниз до `[0, 10000]` и приводит к целому. Backend-наблюдение с `sampleSize: 1` пройдёт валидацию и отрендерится как обычная карточка, наравне с наблюдением на выборке в 30. Клиентский `deriveConclusions` эту дыру не создаёт (у него `MIN_GROUP` встроен в саму генерацию), но если backend когда-либо начнёт присылать `data.observations` независимо от клиентской логики, тонкий bypass по маленькой выборке в UI ничем не блокируется. Это находка для будущего contract review, не багфикс в рамках этой задачи (product code не менялся).

## 5. Недопустимые claims

Существующий продуктовый принцип (`TASKS.md`, `MXL-009`): **не входит** — статистическая причинность, диагнозы, персональные рекомендации по лечению, решение о научной достаточности выборки. Технически это реализовано частично:

- `UNSAFE_INSIGHT_PATTERNS` (`descriptiveInsights.js:1-13`) — regex-фильтр на 11 паттернов: диагноз/расстройство/депрессия/паническ-/лечит/вылечи/вызывает/приводит к/из-за/потому что/гарант-.
- Явный disclaimer в UI на обеих поверхностях, где показываются наблюдения (`Analytics.jsx`, `Settings.jsx` — подтверждено тестом `insights-visibility.test.mjs`).
- Дефолтный caveat на каждое наблюдение без backend-caveat: «Это описание доступных данных, а не диагноз и не доказательство причины.»

**Известное ограничение**, не решаемое этим документом: фильтр — паттерн-мэтчинг по конкретным словоформам, не семантический. Он не поймает переформулировки того же причинного/диагностического claim без этих слов (например, «склонность к тревожности», «риск срыва выше в такие дни» — ни одно слово из списка не встречается, а по сути это тот же причинный/оценочный claim). Это релевантно именно потому, что `data.insights` — LLM-текст, а LLM охотно перефразирует. Флагирую как открытый риск для provenance §3.2 — LLM-канал нуждается либо в более широком semantic-фильтре, либо в отдельном, более консервативном prompt-контракте на backend (вне видимости этого репозитория).

## 6. Метрики perceived usefulness и return intent

### 6.1 Текущее состояние: не измеряется вообще

Ни `deriveConclusions`/`insightDigest`, ни рендер `observations` в `Analytics.jsx` не отправляют ни одного события при показе, прочтении, реакции или переходе. Это полный пробел, не сокращение существующей метрики.

### 6.2 Готовая инфраструктура для переиспользования

В коде уже есть два независимых, проверенных в проде механизма, которые закрывают ровно этот класс задачи для другой фичи (AI-диалог):

1. **`api.events.log(userId, eventType, entityType, entityId)`** (`src/lib/api.js:538-549`) — уже используется для `checkin_morning_start`/`checkin_evening_start` (`CheckIn.jsx`). Не требует нового backend endpoint для добавления новых `eventType`.
2. **`api.mentalix.feedback(userId, rating, messageId)`** + UI-паттерн «Полезно»/«Не полезно» (`Conversation.jsx:132-141, 454-456`) — готовый up/down rating, привязанный к id сообщения, с disabled-состоянием после клика и error-текстом при сбое сети.

### 6.3 Предлагаемые метрики (для решения владельца, не реализовано)

**Perceived usefulness (количественно, по аналогии с §6.2):**

- `insight_shown` / `insight_useful` / `insight_not_useful` события через существующий `api.events.log`, `entity_type = 'observation'`, `entity_id = kind` (нужен стабильный `kind` на каждое наблюдение — сейчас есть только у `data.observations`, не у `data.insights`, см. §3.2).
- Либо прямое переиспользование `api.mentalix.feedback` с новым типом сущности, если backend-контракт это позволяет (не проверено, backend не читался).
- Метрика: `useful / (useful + not_useful)` по типу наблюдения (`kind`) — если у конкретного из 6 правил (§2) стабильно низкое отношение, это сигнал вырезать именно его, а не всю фичу.

**Return intent (сложнее, чем один клик):**

- Прокси-метрика уже частично доступна без нового кода: `mx-insight-seen` (`insightDigest.js:14`) уже хранит дату последнего показа реплики Следопыта локально и в облаке — можно посчитать «открыл ли Analytics/диалог с Следопытом в течение N дней после показа наблюдения», сравнив с общей базой активности, без единого нового event.
- Прямой сигнал требует small-N качественного исследования, а не только телеметрии: «вернулся бы ты сюда специально ради этого» — вопрос про намерение, не измеряемый кликом. Методология уже есть в репозитории и не изобретается заново: `docs/product/STOIC_TO_MENTALIX_AUDIT.md` §5 предлагает для Journal 5–7 пользователей и `complete-cycle rate, return rate, perceived usefulness` — тот же подход прямо переносится на insights, с обязательным соблюдением `docs/research/README.md` (код `P01`–`P05`, согласие, без диагностики со стороны исследователя, без PII в Git).

## 8. Что не входит в этот документ

- Не менялся product code, тесты, backend, API.
- Не создавался и не обсуждался payment/paywall — фича полностью бесплатная в текущем виде, документ этого не меняет.
- Не принято ни одного продуктового решения — какие метрики завести, в каком объёме и когда проводить качественное исследование, решает владелец.
- Не проверялся приватный backend-репозиторий; всё, что зависит от backend-контракта (реальные guards на `data.observations`, реальный prompt для `data.insights`), помечено как непроверенное, а не додумано.

## 9. Рекомендуемые следующие шаги (меню, не решение)

1. Решить, нужен ли явный `kind`/provenance-индикатор для `data.insights`, чтобы purely-LLM наблюдения были отличимы от детерминированных — самостоятельная маленькая задача, до неё не добавлять новые типы правил.
2. Завести `eventType`-схему для `insight_shown`/`insight_useful`/`insight_not_useful` поверх уже существующего `api.events.log` — не требует нового backend endpoint, требует backend-подтверждения хранения новых `event_type`.
3. Посчитать прокси-метрику return intent по уже существующему `mx-insight-seen` без нового кода, как первый дешёвый сигнал до любого нового event.
4. Спланировать 5–7-участниковое качественное исследование return intent по методологии `docs/research/README.md` и прецеденту `STOIC_TO_MENTALIX_AUDIT.md` §5 — отдельная задача с своим consent-протоколом.
5. Закрыть timezone/дата контракт (`MXL-JOURNAL-HISTORY-001_ARCHITECTURE.md` §7) до того, как принимать решения по паттернам, зависящим от календарного дня (правило №5, возможно другие в будущем).
6. Если backend когда-либо начнёт присылать `data.observations` из независимого источника (не клиентского `deriveConclusions`) — закрыть пробел §4.2 нижней границей `sampleSize` в `sanitizeObservations`.
