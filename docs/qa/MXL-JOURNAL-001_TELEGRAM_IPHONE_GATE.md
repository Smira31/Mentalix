# MXL-JOURNAL-001 — Telegram/iPhone gate

**Назначение:** инструкция владельцу Mentalix для ручной проверки PR #237 — read-only отображения local-first journal в History.

**Статус:** рабочий gate-документ. Он фиксирует воспроизводимый процесс, но не заменяет фактическую проверку на реальном устройстве. Скриншоты не должны содержать реальные личные записи, Telegram initData, токены, URL с секретами или персональные данные.

## 1. Что именно проверяется

Проверяется только local-first mini-slice:

- сегодняшняя запись журнала читается через `readJournalEntry(date)`;
- History безопасно отображает состояния `empty`, `partial` и `final`;
- заполненные фазы показываются с русскими названиями и статусом `черновик`/`завершено`;
- повреждённый local storage не роняет History;
- PR не создаёт ложного статуса cloud sync и не добавляет новый backend request.

Cloud sync, серверное хранение, export/delete, retention и передача текста в AI этим gate не проверяются.

## 3. Сценарий A — пустое состояние

Цель — проверить `LS-EMPTY-001` на пользовательском экране.

1. В тестовом аккаунте открыть History.
2. Убедиться, что для сегодняшнего дня нет journal-текста.
3. Проверить, что History не показывает пустую карточку как заполненный journal.
4. Проверить, что экран не падает, не показывает `NaN`, `undefined`, технический JSON или ложное «синхронизировано».
5. Если есть общий empty state History, проверить, что он остаётся читаемым и не перекрывается карточкой журнала.
6. Вернуться в Journal Home, не вводить текст и снова открыть History.

**Ожидаемый результат:** приложение работает, empty state понятен, незаполненные фазы не выдаются за завершённую запись.

**Обязательный скриншот:** `01-history-empty.png` — History в пустом состоянии, без личных данных.

## 4. Сценарий B — частичный draft

1. Открыть Journal Home.
2. Ввести безопасный тестовый текст в фазу «Идея», например: `Тестовая идея для проверки History.`
3. Не использовать реальные мысли, имена, адреса, медицинские сведения или приватную переписку.
4. Перейти к следующей фазе или закрыть экран так, чтобы запись осталась draft.
5. Открыть History.
6. Проверить заголовок `Журнал · 1/4` или соответствующее фактическое число заполненных фаз.
7. Убедиться, что отображается текст «Идея» со статусом `черновик`.
8. Убедиться, что пустые фазы не показываются как заполненные и не получают статус `завершено`.
9. Закрыть Telegram/WebView, снова открыть тот же Preview и повторить пункт 5.

**Ожидаемый результат:** draft переживает повторный вход, отображается только фактически заполненная фаза, History не обещает cloud sync.

**Обязательные скриншоты:**

- `02-journal-partial.png` — Journal Home с частичным draft;
- `03-history-partial.png` — History с одной заполненной фазой и статусом `черновик`;
- `04-history-partial-reopen.png` — тот же partial draft после повторного открытия Telegram/WebView.

## 5. Сценарий C — полный цикл и final status

1. В Journal Home ввести разные безопасные тексты во все четыре фазы:
   - «Идея»;
   - «Действие»;
   - «Анализ»;
   - «Новый шаг».
2. Завершить последний шаг штатной CTA.
3. Открыть History.
4. Проверить, что заголовок показывает `4/4`.
5. Проверить наличие всех четырёх фаз в правильном порядке.
6. Проверить, что финальная фаза показывает `завершено`, а предыдущие статусы соответствуют фактическому storage.
7. Закрыть и снова открыть Telegram Mini App.
8. Убедиться, что текст не исчез, не перемешался между фазами и не появился второй дубликат записи.

**Обязательные скриншоты:**

- `05-journal-complete.png` — Journal Home после завершения цикла;
- `06-history-complete.png` — History с четырьмя фазами;
- `07-history-complete-reopen.png` — восстановленный полный цикл после повторного входа.

## 6. Сценарий D — corrupted local storage

Этот сценарий нужен только если вы умеете безопасно открыть DevTools/remote WebView inspector для тестового Preview. Не выполняйте его через production и не изменяйте реальные пользовательские данные.

1. Открыть DevTools для Preview PR #237.
2. В Application/Storage найти ключ `mx-journal-v2`.
3. Сохранить исходное тестовое значение в локальный временный файл или записать, что storage был пустым.
4. Заменить значение только тестового ключа на безопасную строку `{broken-json`.
5. Перезагрузить History.
6. Проверить, что экран не падает, не показывает stack trace и возвращает безопасное пустое состояние.
7. Проверить, что значение не было молча заменено на другой пользовательский текст.
8. После проверки удалить тестовое corrupted значение или очистить только тестовый storage.
9. Снова открыть Journal Home и убедиться, что тестовый аккаунт работает.

**Ожидаемый результат:** `LS-CORRUPT-001` проходит: History остаётся работоспособным, показывает безопасный fallback и не публикует содержимое storage в UI.

**Обязательные скриншоты:**

- `08-corrupted-history-safe-fallback.png` — History после повреждённого JSON, без DevTools с секретами;
- `09-corrupted-recovered.png` — восстановленный рабочий экран после очистки тестового значения.

Если remote inspector недоступен, не имитируйте этот сценарий в пользовательском интерфейсе. Отметьте `NOT TESTED — inspector unavailable`; автоматический тест остаётся источником проверки corrupted JSON.

## 7. Мобильная вёрстка и Telegram lifecycle

Проверить на вертикальном iPhone:

- safe area сверху и снизу не перекрывает History;
- нет горизонтального overflow;
- текст не обрезается за пределами карточки;
- длинная строка переносится без выхода за viewport;
- после сворачивания Telegram и возврата экран не становится пустым;
- системный back не закрывает Mini App неожиданно;
- повторное открытие Preview не создаёт вторую journal-запись.

Для каждого blocker записать шаг воспроизведения, ожидаемый результат, фактический результат и screenshot filename.

## 10. Решение gate

**PASS** — только если Preview соответствует PR #237, empty/partial/full состояния не теряют контекст, corrupted fallback не роняет History, мобильная вёрстка читаема, cloud sync не заявляется без реализации и нет утечки личных данных в кадре.

**FAIL** — при потере или смешивании текста, падении History, ложном статусе cloud sync, невозможности восстановить draft, горизонтальном overflow, перекрытии клавиатурой, неожиданном network/AI handoff или проверке не того Preview.

**NOT TESTED** — допустимо только для optional corrupted-storage inspector, если инструмент недоступен. Это не равно PASS.

После отчёта merge PR #237 не выполнять автоматически: сначала сохранить результат в PR и отдельно принять решение владельца.
