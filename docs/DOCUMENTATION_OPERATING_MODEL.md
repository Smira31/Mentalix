# Documentation operating model

Этот документ задаёт границы между нормативными документами, текущим backlog и историей проекта. Он не заменяет GitHub Issues или Project board.

## Источник истины по статусу

| Вопрос | Канонический источник | Что хранится |
| --- | --- | --- |
| Что нужно сделать и каков текущий статус | GitHub Issues и Project board | open, in progress, blocked, closed, priority и assignee |
| Как устроен продукт и какие решения приняты | `PRODUCT.md`, `ARCHITECTURE.md`, `DESIGN_SYSTEM.md`, `docs/core/PRODUCT_DECISIONS.md` | действующие правила и решения |
| Что изменилось в уже опубликованной истории | `CHANGES.md` | короткая запись результата, PR и evidence |
| Почему задача появилась и как развивалась | `TASKS.md` | исторический контекст и ссылки, без копирования текущего статуса |
| Какой порядок работ был выбран | `ROADMAP.md` | этапы и критерии перехода между ними |

`docs/TASK_INDEX.md` остаётся навигационным индексом активного backlog, но не дублирует карточки Issues. Если локальный документ расходится с GitHub, действуют правила из `AI_RULES.md`: discrepancy фиксируется, а не исправляется молча.

## Правило для TASKS.md и CHANGES.md

`TASKS.md` отвечает на вопрос «почему и в каком контексте появилась работа». `CHANGES.md` отвечает на вопрос «какой подтверждённый результат опубликован». Одна и та же запись не должна пересказывать полный текст дважды.

Новая историческая запись должна содержать идентификатор Issue, ссылку на PR, одну фразу о результате и ссылку на evidence. Подробный scope, критерии и открытые блокеры остаются в Issue. Если результат меняет принятое продуктовое решение, подробность помещается в соответствующий decision-документ, а в `CHANGES.md` добавляется только ссылка.

При обновлении старых записей применяется безопасная последовательность: сначала добавить ссылки и проверить, что информация не потеряна; затем убрать дословный повтор; после этого запустить `npm run docs:check`. Исторические даты, идентификаторы PR и сведения о блокерах нельзя удалять без явной замены ссылкой на источник.

## Стиль нормативного текста

Длинный абзац следует разбивать, если он содержит более одной самостоятельной мысли, условие и исключение или больше трёх действий. Для сравнений и повторяющихся полей используется таблица; для последовательности действий — нумерованный список; для ограничений — короткий маркированный список.

Нормативная секция должна начинаться с одного предложения о назначении, затем содержать правила и отдельный блок исключений или границ. Примеры и исторические объяснения маркируются как examples или history и не смешиваются с обязательными правилами.

## Минимальная запись изменения

```markdown
- `MXL-XXX` — результат в одном предложении; [PR #N](https://github.com/Smira31/Mentalix/pull/N); evidence: `path/to/evidence`.
```

Такой формат оставляет журнал сканируемым, сохраняет трассируемость и не превращает `TASKS.md` и `CHANGES.md` в второй backlog.
