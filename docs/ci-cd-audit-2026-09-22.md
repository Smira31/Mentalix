# Mentalix CI/CD audit — 2026-09-22

## Scope and method

Аудит выполнен для ветки `main` репозитория `Smira31/Mentalix` 22 сентября 2026 года. Проверены все семь YAML-файлов в `.github/workflows/`, состояние workflows в GitHub Actions, branch protection для `main`, active repository ruleset, ссылки на production/QA-инфраструктуру в репозитории и последние доступные запуски.

Среднее время — арифметическое среднее продолжительности последних примерно 15 запусков, доступных через GitHub Actions API на момент аудита. Для отключённых workflows запусков в текущем окне нет; это указано явно. GitHub Actions также показывает системный `Dependabot Updates`; он управляется конфигурацией `.github/dependabot.yml`, а не YAML workflow в `.github/workflows/`, поэтому приведён отдельно.

## Required checks

В branch protection для `main` сейчас задан единственный required context: **`Функциональная проверка проекта`** (job `required-check` в `Mentalix CI baseline`). Включённый ruleset «Защита главной ветки Mentalix» активен; strict required status checks включены. Ни Cloudflare Owner QA, ни Firebase Hosting, ни visual snapshot job не являются required checks.

До этой доработки job `required-check` зависел только от `quality` и `backend-health`, а `Playwright Chromium smoke` мог падать независимо; то есть фактический Playwright functional smoke не входил в required gate, несмотря на название workflow. В этой ветке `required-check` дополнительно проверяет результат `ux`, а visual job остаётся отдельным informational job с `continue-on-error: true` и не добавляется в required contexts.

## Disabled workflows: interpretation

Все четыре названных отключённых workflow имеют в GitHub Actions состояние **`disabled_manually`**, а не `disabled_inactivity`. Это означает, что они были отключены вручную и сейчас не ждут автоматического запуска: `Issue triage`, `PR handoff report`, `Telegram Owner QA Web App` и `Создать релиз Mentalix`. В репозитории нет расписания или триггера, который сам их возобновит. Рекомендация — не удалять их в рамках этого PR, а принять отдельное владельческое решение по таблице выше; наиболее безопасная последовательность — сначала проверить, используется ли соответствующий operational flow, затем удалить или восстановить только нужные.

## Cloudflare versus Firebase finding

Production действительно настроен на Firebase Hosting: workflow деплоит `live` channel и проверяет `https://mentalix-production.web.app/`. Однако Cloudflare не является мёртвым остатком: `cloudflare-owner-qa.yml` непосредственно вызывает `cloudflare/wrangler-action`, Cloudflare API и проверяет `mentalix-owner-qa.pages.dev`; `telegram-owner-qa-webapp.yml` использует тот же контур; `tests/unit/maintenance-contracts.test.mjs` также фиксирует Cloudflare Owner QA контракт. Поэтому вывод «Cloudflare больше нигде не используется» был бы неверен. Корректнее считать Cloudflare **не production**, а отдельным Owner QA контуром.

## Snapshot split implemented in this PR

В `tests/ux/ux-check.spec.mjs` добавлен флаг `RUN_VISUAL_SNAPSHOTS`:

- `Mentalix CI baseline / Playwright Chromium smoke` запускается с `RUN_VISUAL_SNAPSHOTS=false`; функциональные сценарии и существующие functional assertions остаются в этом job.
- Новый `Playwright visual snapshots (informational)` запускается с `RUN_VISUAL_SNAPSHOTS=true`; он выполняет тот же существующий набор сценариев и включает только существующие `toHaveScreenshot` anchor-сравнения.
- Visual job имеет `continue-on-error: true`, отдельные artifacts и не добавлен в Required checks.
- `Функциональная проверка проекта` теперь явно проверяет результат `ux`, поэтому functional Playwright smoke действительно входит в текущий required gate; required context и его статус в branch protection не менялись.
- Список сценариев и snapshot baselines не менялись.

## Verification plan/results

Проверка выполнена локально на ветке PR. `npm run lint`, `npm run test:unit`, `npm run build` и Prettier прошли. Functional mode (`RUN_VISUAL_SNAPSHOTS=false`) дал **9 passed, 1 skipped**; в нём нет вызовов `toHaveScreenshot`. Visual mode (`RUN_VISUAL_SNAPSHOTS=true`) дал **8 passed, 1 skipped, 1 flaky**: единственный сигнал — ожидаемый snapshot diff `Practices` на `375x812`, без функционального падения. На исходном `main` последний production-like CI запуск также падал именно на `toHaveScreenshot` для `Practices` в `375x812`, `390x844` и `430x932`; это подтверждает необходимость разделения.

После запуска PR workflow ожидается:

1. `Playwright Chromium smoke` — PASS при отсутствии functional/runtime/geometry/assertion regressions.
2. `Функциональная проверка проекта` — PASS только если `quality`, `backend-health` (или skipped по scope) и `ux` успешны.
3. `Playwright visual snapshots (informational)` — может быть `failure`, если существующие baselines расходятся, но это не Required check и не блокирует merge.
