# Проверка UI Mentalix на разных разрешениях экранов

Инструкция предназначена для ручной проверки Telegram Mini App на реальных устройствах и для сопоставления с локальным UX smoke. Она помогает отличить реальный дефект layout от особенностей Telegram WebView, клавиатуры iOS или конкретного scroll-положения.

## 1. Матрица устройств

| Профиль           | Пример                                        | Минимум проверки                                                                             |
| ----------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Узкий и низкий    | iPhone SE 2, 320×568 CSS px                   | Нет горизонтального overflow; нижняя навигация и CTA доступны; длинные заголовки переносятся |
| Узкий современный | iPhone 13 mini, около 375×812 CSS px          | Safe area, Dynamic Island/notch, клавиатура, модальные окна                                  |
| Стандартный       | iPhone 14/15/16, около 390×844 CSS px         | Полный core loop и все пять вкладок                                                          |
| Высокий           | iPhone 14/15/16 Pro Max, около 430×932 CSS px | Верхний scroll offset, нижний dock, большие пустые области                                   |
| Android-контроль  | Современный Android с Telegram                | Только если входит в release scope; отдельно проверять системные insets и клавиатуру         |

Фактические размеры устройства нужно записывать вместе с моделью, ОС, версией Telegram, URL/commit и датой. Нельзя считать desktop viewport заменой реального Telegram/iPhone gate.

## 2. Подготовка

Перед проверкой открыть production или явно обозначенный Preview из Telegram WebView, а не в обычном Safari/Chrome. Использовать тестовый аккаунт без публикации приватных записей. Зафиксировать начальное состояние, URL, commit если он известен, модель устройства, ОС и версию Telegram.

В каждом профиле очистить случайное состояние только если это разрешено тестовым сценарием. Не удалять production-данные и не менять настройки backend ради теста.

## 3. Базовая последовательность

Проверять экраны в одинаковом порядке: запуск → Today → Check-in → Practices → Mentor/AI → Library → Trends → закрытие Mini App и повторное открытие. На каждом экране выполнить проверку в верхнем, среднем и нижнем положении scroll.

| Шаг                      | Ожидаемый результат                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| Запуск из Telegram       | WebView открывается без белого экрана, краша или лишнего горизонтального scroll           |
| Верх экрана              | Заголовок, первый контент и Telegram chrome не накладываются друг на друга                |
| Нижняя часть             | CTA, нижняя навигация и системный Home Indicator не перекрывают друг друга                |
| Поворот/изменение высоты | Если устройство или Telegram изменили доступную высоту, layout перестраивается без скачка |
| Переходы                 | Контент не мигает и не прыгает к неожиданному scroll offset                               |
| Закрытие                 | Кнопка «Закрыть» возвращает в Telegram без краша; повторный запуск загружает приложение   |

## 4. Safe area и фиксированные элементы

Проверить, что верхний контент не попадает под notch или Dynamic Island, а нижняя навигация и кнопки находятся выше Home Indicator. Открыть экран с длинным содержимым и прокрутить его до конца: фиксированный header не должен скрывать первую строку, а fixed dock не должен закрывать активное поле или CTA.

Особое внимание уделить трём наблюдаемым рискам Mentalix:

1. На экране «Наставник» и в журнале проверить, не уходит ли начало текста под верхний header после открытия, возврата и прокрутки.
2. На Writing Canvas с открытой клавиатурой проверить, не перекрывает ли нижний dock активное поле, кнопку «Пойти глубже» или кнопку завершения.
3. На узком экране проверить, не прижат ли floating control к правому краю и не обрезается ли его hit area.

## 5. Клавиатура и ввод

На Check-in и AI Dialog открыть поле, ввести короткий и длинный текст, нажать Return, закрыть клавиатуру и снова открыть её. Зафиксировать, остаётся ли активное поле видимым, не изменяется ли неожиданно scroll offset и не перекрываются ли кнопки.

Для каждого текстового сценария проверить: перенос длинной строки, отсутствие горизонтального overflow, сохранение текста после смены фокуса, доступность кнопки отправки и корректное возвращение viewport после закрытия клавиатуры.

## 6. Визуальные критерии PASS/FAIL

| Критерий         | PASS                                                      | FAIL                                               |
| ---------------- | --------------------------------------------------------- | -------------------------------------------------- |
| Центрирование    | Заголовки, карточки и CTA соответствуют design baseline   | Элемент заметно смещён или обрезан                 |
| Safe area        | Нет наложения на Dynamic Island, notch или Home Indicator | Контент/кнопка скрыта системной областью           |
| Scroll           | Верх и низ контента доступны                              | Первая/последняя строка скрыта fixed-элементом     |
| Keyboard layout  | Поле и действие доступны во время ввода                   | Keyboard/dock закрывают поле или CTA               |
| Responsive width | Нет горизонтального overflow                              | Текст, карточка или control выходит за viewport    |
| Motion           | Переход и появление keyboard не вызывают видимого скачка  | Layout прыгает, мерцает или теряет scroll position |
| Touch target     | Кнопки легко нажимаются и не перекрываются                | Нажатие попадает в соседний control или недоступно |
| Контраст         | Вторичный текст читается в обычном освещении              | Текст практически сливается с фоном                |

## 7. Как фиксировать дефект

Для каждого FAIL записать устройство, CSS viewport если известен, экран, начальное действие, ожидаемый результат, фактический результат, повторяемость и screenshot/screen recording. Один дефект — одна запись. Не называть проблему «прыгает» без описания момента: например, «после открытия клавиатуры header смещается на 24 px и первая строка скрывается».

Минимальный шаблон:

```text
ID проверки:
Дата:
Устройство / реальный viewport:
ОС:
Telegram:
URL / commit:
Экран:
Шаги воспроизведения:
Ожидалось:
Фактически:
Повторяемость: 1/1, 3/3 или плавающая
Severity: blocker / major / minor / polish
Evidence: screenshot или video
```

## 8. Release decision

`PASS` означает, что обязательные экраны проверены на согласованных профилях и не имеют blocker/major дефектов. `PASS with notes` допустим только для явно документированного визуального polish, который не скрывает контент и не ломает действие. Любой дефект safe area, недоступная CTA, потеря введённого текста, краш или горизонтальный overflow блокирует release gate до решения владельца.

Зелёные CI, Vercel Preview и desktop smoke не закрывают ручной gate. Для Telegram/iPhone требуется подтверждение владельца с датой и профилем устройства.
