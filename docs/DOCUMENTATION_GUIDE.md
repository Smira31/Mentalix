# Mentalix — Documentation Operating Guide

Статус: нормативный рабочий гайд для владельца и AI-агентов. Этот файл описывает, **как читать и обновлять документацию**, но не меняет продуктовые решения.

## 1. Быстрый маршрут чтения

| Вопрос                                      | Источник                                                      | Что считать фактом                                                          |
| ------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Что это за продукт и для кого?              | [`PRODUCT.md`](../PRODUCT.md)                                 | Принципы, ежедневный цикл, открытые продуктовые решения                     |
| Что реально работает сейчас?                | [`PROJECT_STATE.md`](../PROJECT_STATE.md)                     | Последний подтверждённый GitHub/production/runtime state и release blockers |
| Что делать дальше?                          | [`TASKS.md`](../TASKS.md)                                     | Только актуальные задачи, их scope, статус и критерии готовности            |
| В каком порядке двигаться?                  | [`ROADMAP.md`](../ROADMAP.md)                                 | Этапы и кандидаты; это не самостоятельное разрешение на реализацию          |
| Какие правила обязательны?                  | [`AI_RULES.md`](../AI_RULES.md) и [`AGENTS.md`](../AGENTS.md) | Границы изменений, тестовый цикл, PR и decision gates                       |
| Какие токены и UI-контракты использовать?   | [`DESIGN_SYSTEM.md`](../DESIGN_SYSTEM.md)                     | Фактическая визуальная система                                              |
| Как устроен frontend и где границы backend? | [`ARCHITECTURE.md`](../ARCHITECTURE.md)                       | Слои, API-границы и технический долг                                        |
| Что уже изменилось?                         | [`CHANGES.md`](../CHANGES.md)                                 | Краткая подтверждённая история; не источник текущего статуса                |

**Правило по умолчанию:** сначала `PROJECT_STATE.md`, затем `TASKS.md`, затем профильный документ и код. Если они расходятся, не угадывать: зафиксировать расхождение и остановиться.

## 2. Жизненный цикл задачи

Каждая задача должна иметь один стабильный ID и одну каноническую запись в `TASKS.md`. В записи указываются цель, размер, тип (`product`, `ux`, `technical`, `research`, `release`), зависимости, решение владельца, критерии готовности и текущий статус.

Рекомендуемый формат:

```markdown
## MXL-EXAMPLE-001 — Короткое название

- **Статус:** backlog | ready | in progress | PR | merged | blocked | cancelled
- **Размер:** XS | S | M | ML | L
- **Тип:** product | ux | technical | research | release
- **Автономность:** yes | needs-owner | manual-gate | backend-dependent
- **Цель:** какую проблему решаем.
- **Не входит:** что намеренно не меняем.
- **Зависимости:** решения, backend, данные, ручные проверки.
- **Критерии готовности:** наблюдаемые результаты.
- **Проверки:** команды и ручные gates.
- **Rollback:** как отменить изменение.
- **Результат:** PR, commit, дата и ограничения проверки.
```

Жизненный цикл: `backlog → ready → in progress → PR → checks passed → merged → verified`. Статусы `blocked`, `needs-owner` и `manual-gate` не должны автоматически превращаться в `ready`.

## 3. Категории автономности

| Категория           | Можно делать без нового решения?                    | Примеры                                                                                             |
| ------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `autonomous`        | Да, если scope уже принят и diff минимален          | документация, maintenance, regression test, очевидный bugfix без UX/API-решения                     |
| `needs-owner`       | Нет                                                 | новая пользовательская функция, изменение навигации, AI-тональности, бренда или поведения core loop |
| `manual-gate`       | Код может быть готов, но закрытие требует владельца | Telegram/iPhone, keyboard, safe area, real-user validation                                          |
| `backend-dependent` | Нет без приватного backend-контракта                | API, auth, безопасность, события, миграции и данные                                                 |

## 4. Обязательный handoff

В конце каждой существенной задачи агент обновляет `TASKS.md` и `PROJECT_STATE.md`; в `CHANGES.md` добавляется короткая ссылка на каноническую запись. Историю не переписывать: устаревший факт корректируется новой dated-записью с объяснением.

Минимальный handoff должен отвечать на пять вопросов: что изменилось, где это находится, какие проверки прошли, какие проверки не выполнялись и какой следующий decision gate.

## 5. Release snapshot

`PROJECT_STATE.md` должен содержать отдельный компактный snapshot с датой проверки: GitHub `main` SHA, production URL, подтверждённый deployment SHA (если известен), health status, открытые blockers и последнюю ручную проверку. Нельзя смешивать «HTTP 200», «deployment Ready» и «этот deployment построен из данного SHA» — это разные утверждения.

## 6. Правила каталога

Исторические задачи и идеи не должны выглядеть как текущий backlog. Закрытые записи остаются в истории, но текущий раздел `TASKS.md` должен иметь короткий индекс активных задач с фильтрами по статусу, размеру и автономности. Большие audit-документы и problem research должны ссылаться на ID, а не создавать новые почти одинаковые ID.

Для каждого нового ID перед созданием проверить `git grep` и существующие Issues/PR. Если похожая задача уже есть, обновить её запись вместо создания дубликата.

## 7. Границы этого гайда

Этот документ не утверждает новые продуктовые решения, не выбирает P0 и не заменяет ручной iPhone/Telegram gate. Он только делает правила работы с уже существующей документацией более явными и пригодными для передачи между агентами.
