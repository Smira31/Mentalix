# Mentalix — AI Rules v1

Эти правила применяются к ChatGPT, Codex и другим AI-агентам, работающим с Mentalix.

## 1. Сначала факты

Перед предложением изменений:

1. прочитать `PRODUCT.md`, `DESIGN_SYSTEM.md`, `ARCHITECTURE.md`, `ROADMAP.md`;
2. изучить фактические связанные файлы;
3. назвать затрагиваемые сценарии и контракты;
4. отделить факт кода от гипотезы и рекомендации.

Если backend недоступен, прямо указать, какие приватные файлы нужны. Не выдумывать контракт.

## 2. Граница разрешения

Без явного согласования нельзя:

- менять продуктовую логику;
- менять визуальный язык, токены, шрифт или тексты бренда;
- добавлять/удалять основные вкладки;
- менять AI-персоны;
- менять API-контракты;
- менять оплату, безопасность, возрастные ограничения;
- включать новую зависимость или архитектурный слой.

Разрешённая документационная работа не означает разрешение исправлять код.

## 3. Формат предложения

До реализации предоставить:

- цель;
- наблюдаемое текущее поведение;
- затрагиваемые файлы;
- что изменится для пользователя;
- что точно не изменится;
- риски и неизвестные;
- способ проверки;
- rollback.

## 4. Правила реализации

- Делать минимальный цельный diff.
- Не смешивать функциональную, визуальную правку и рефакторинг.
- Сохранять Telegram и web.
- Не ломать safe areas, fullscreen, keyboard и bottom navigation.
- Переиспользовать фактические токены.
- Не копировать референс буквально.
- Не «улучшать заодно».
- Не удалять legacy-код без проверки потребителей.
- Не печатать секреты, токены, персональные данные или raw auth payload.

### 4.1. Размер тестового цикла

- В один тестовый цикл включать не более двух пользовательских функций.
- Обе функции должны относиться к одной пользовательской проблеме или одному ежедневному сценарию.
- Для каждой функции заранее задавать отдельный наблюдаемый результат, чтобы их влияние не смешивалось.
- Исправления критических дефектов текущего цикла не считаются новой пользовательской функцией.
- Больше двух функций допускается только после отдельного явного решения владельца.

## 5. Проверка

Минимум для любого изменения:

- `npm run build`;
- проверка изменённого сценария;
- loading/error/empty;
- mobile viewport;
- light/dark, если затронут UI;
- Telegram и web, если затронут platform layer.

Для fixed/sticky/keyboard/fullscreen изменений обязательна проверка на реальном iPhone в Telegram.

## 6. Работа с документами

- `PRODUCT.md`: зачем, кому, принципы и решения;
- `DESIGN_SYSTEM.md`: фактические токены и UI-правила;
- `ARCHITECTURE.md`: устройство и границы;
- `ROADMAP.md`: порядок и критерии;
- `AI_RULES.md`: процесс работы;
- `REFERENCE_WORKFLOW.md`: перевод референсов;
- `TASKS.md`: только текущая работа;
- `CHANGES.md`: подтверждённые изменения.

## 6.1. Автоматическое закрытие задачи

Каждая задача проходит обязательный цикл:

1. реализовать согласованный scope;
2. выполнить доступные проверки;
3. зафиксировать результат в `CHANGES.md`;
4. **обязательно** обновить статус в `TASKS.md` — без исключений, это шаг закрытия задачи, а не опциональная документация;
5. обновить `ROADMAP.md`, только если изменился этап, приоритет или критерий завершения;
6. открыть отдельный PR и не сливать без подтверждения пользователя.

Задача не считается полностью закрытой, пока её статус не отражён в `TASKS.md` — это единственный источник актуальной работы. Для чисто исследовательской задачи без изменения проекта достаточно отчёта; `CHANGES.md` и `ROADMAP.md` обновляются дополнительно, если исследование изменило принятое решение или статус roadmap.

Перед началом новой самостоятельной задачи Codex оценивает размер текущего чата. Если в нём уже смешано несколько завершённых задач или большой объём проверок, Codex рекомендует новый чат и даёт готовый стартовый запрос.
Если документ расходится с кодом, не выбирать молча. Зафиксировать discrepancy и запросить решение.

## 7. Definition of Done

Задача завершена, когда:

- согласованный scope реализован;
- неожиданных изменений нет;
- сборка проходит;
- сценарий проверен;
- ограничения проверки перечислены честно;
- документация обновлена только там, где решение действительно изменилось.

## 8. Запрещённые формулировки

Не утверждать «готово», если проверена только сборка.  
Не утверждать «backend поддерживает», если приватный backend не изучен.  
Не утверждать «по дизайн-системе», если использованы значения не из фактических токенов.  
Не превращать рекомендацию в принятое решение.

## 9. Технические инварианты

Выведены из ревизии 05.08.2026, где каждый пункт был найден размноженным
по нескольким файлам. Нарушение любого — повод остановиться, а не обойти.

| Инвариант | Правило | Почему |
|---|---|---|
| **Платформа** | Единственная точка входа в Telegram SDK — `src/platform/`. Прямой импорт `@twa-dev/sdk` вне этого каталога запрещён и падает на ESLint. Не заводить локальную обёртку над `WebApp`, даже в три строки. | Именно так появилось восемь копий `haptic`, шесть из которых умели только `impactOccurred` и молча теряли отклик на успех и ошибку. |
| **Время** | Таймер считается от отметки времени (`Date.now()`), а не сложением тиков `setInterval`. Для участия пользователя (дыхание, упражнения) время дополнительно встаёт на паузу при скрытом экране. | Вебвью Telegram душит таймеры в фоне, счётчик отстаёт от реальности; заблокированный телефон не должен засчитывать практику за человека. |
| **Побочные эффекты** | Внутри апдейтера `setState(x => ...)` не вызывать ничего, кроме вычисления нового значения — ни API, ни другие сеттеры, ни `clearInterval`. Завершения и записи — отдельным эффектом с защитой через `useRef`. | В StrictMode апдейтер вызывается дважды — так сессия фокуса писалась в статистику дублем. |
| **Текст** | Иерархия задаётся токенами `text-cream` / `text-muted` / `text-faint`, а не прозрачностью. Прозрачность у текста допустима только как анимация. Подробности и пороги — `DESIGN_SYSTEM.md`, раздел «Шкала текста». | Прозрачность как статичная иерархия визуально похожа на приглушённый текст, но даёт недостаточный контраст (пример: `text-cream/35` ≈ 2.8:1). |
| **Документы** | Значения токенов — шрифт, цвета, уровни — живут в `DESIGN_SYSTEM.md` и больше нигде. Остальные документы ссылаются, но не дублируют. | Продублированное значение расходится с кодом — вопрос времени, а не аккуратности. |
| **Журналы** | `TASKS.md` — единственный источник полного технического описания текущей и недавно закрытой работы (что сделано, файлы, PR, проверка). Запись в `CHANGES.md` для задачи, закрытой начиная с 08.08.2026, — дата, короткий итог (1–3 строки) и ссылка на соответствующий раздел `TASKS.md`, без повторения технического описания. `docs/engineering/JOURNAL.md` продолжает вести полную хронологию. Отменённые/устаревшие решения не переписываются под текущее состояние — фиксируется новая запись поверх, а не правка старой. | До 12.08.2026 `CHANGES.md` дублировал `TASKS.md` почти дословно для каждой закрытой задачи — один и тот же факт (PR, коммит, проверка) поддерживался в двух местах и расходился быстрее, чем кто-то успевал сверить оба. Само правило обновлено 12.08.2026 вместе с переходом на новый формат — правило и практика меняются одним шагом, не одно без другого. |
| **Контракты хуков** | При использовании общего хука (например `useFullscreenSurface`) экран обязан импортировать и использовать его напрямую, а не копировать константы/логику локально под своим именем. | Локальная копия расходится с хуком при любой будущей правке — тот же класс проблемы, что восемь копий `haptic` (см. инвариант «Платформа»). Найдено 16.08.2026 в `CheckIn.jsx` при аудите `MXL-UI-005`. |
| **Динамические Tailwind-классы** | Не собирать имя Tailwind-класса из переменной на лету (например `` `bg-${color}` ``). Tailwind видит только классы, присутствующие в исходниках буквально при сборке. | Динамически собранная строка не попадёт в CSS-бандл, и класс не сработает — скрытый баг, который не проявляется в dev, но ломает стиль в production-сборке. |
