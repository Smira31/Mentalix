# Security Policy

## Supported version

Security fixes are applied to the current `main` branch and the current Firebase Production deployment. Old commits, historical previews and archived deployments are not supported versions.

## Report a vulnerability privately

Use GitHub's private **Report a vulnerability** form in the repository's **Security** tab.

Do not open a public Issue, pull request or Discussion for a suspected vulnerability. Public reports can expose users before a fix is ready.

Include, when possible:

- a short description and expected impact;
- safe reproduction steps;
- the affected URL, commit or component;
- the browser, device and runtime context;
- screenshots or logs with secrets and personal data removed;
- any suggested mitigation.

Never include passwords, tokens, private keys, real authentication codes or another person's private data. Do not access, alter or download user data to prove a finding, and do not disrupt Production or external services.

## What belongs in a security report

Examples include unauthorized access, authentication or session bypass, exposure of secrets or private user data, injection, cross-site scripting, unsafe deployment configuration and exploitable dependency vulnerabilities.

Visual defects, feature requests and ordinary product bugs should use the normal GitHub Issue templates instead.

## Handling and disclosure

The maintainer will review the private report, request clarification when needed and coordinate a fix before public disclosure. Please keep the report private until the maintainer confirms that disclosure is safe.

This project does not currently promise a response-time SLA or a vulnerability bounty.
