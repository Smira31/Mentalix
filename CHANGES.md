## Закрыто 13.08.2026 — MXL-DEFAULT-CONTENT-001: сидирование воспроизведено, root cause подтверждён

- Продолжение записи от 12.08 ниже. Проверка `getWebhookInfo` показала: `url` пустой, вебхука нет — гипотеза «перехват апдейтов через webhook» исключена, бот действительно работает через polling.

- Прямой запрос в БД подтвердил успешное сидирование: `users` — новая строка (`id=8348817724`, `created_at=2026-08-13 05:42:21`); `ascezas` — 3 строки с тем же timestamp (Алкоголь/Никотин/Думскроллинг, `category='psycho'`, `relapse_cost` заполнен); `rituals` — 3 новые строки с тем же timestamp (Холодный душ/Тишина и благодарность утром/Физическая нагрузка).
- **Root cause подтверждён:** конфликт токена `getUpdates` (см. запись от 12.08) был единственной причиной отсутствия сидирования — после перевыпуска токена `@Mentalix_club_bot` функция воспроизводится штатно при живом `/start`. Задача закрыта, подробности — `TASKS.md` → `Completed / Archived` → `MXL-DEFAULT-CONTENT-001`.
- Побочная находка при проверке БД: два ритуала (`id 15, 16`, дата `2026-08-11`) — осиротевшие остатки более раннего ручного REST-теста, висят на том же `user_id`, не относятся к сегодняшнему сидированию. Вынесено отдельной задачей `MXL-ORPHAN-RITUALS-001` в `TASKS.md` → «Позже» (почистить строки вручную + рассмотреть FK-ограничение `rituals.user_id → users.id`, которого сейчас в схеме нет).

## Зафиксировано 12.08.2026 — MXL-DEFAULT-CONTENT-001: на паузе, root cause найден, устранение частично подтверждено

- Реализация (backend, `mentalix-bot` PR #2, squash-коммит `e41f71e`) не менялась и уже задеплоена — сидирование 3 ритуалов + 3 аскез для нового пользователя внутри `if user is None:` в `cmd_start`.
- Живая проверка на реальном втором Telegram-аккаунте (`andre_smi3`) упёрлась в отдельный, не связанный с этим кодом баг инфраструктуры: `TelegramConflictError`/`409` на `getUpdates` у `@Mentalix_club_bot` — сторонний процесс где-то перехватывал апдейты (включая тестовые `/start`) раньше продового Railway-инстанса `accurate-expression`, из-за чего `cmd_start` вообще не вызывался для тестового пользователя (строка в `users` не создавалась).
- Разбор методом исключения: подтверждено прямыми запросами к БД (`users` пуст), логами Railway (`--since 2h` — только 7 строк деплой-старта, ноль активности при реальных `/start`), read-only вызовами Telegram Bot API (`getWebhookInfo` — вебхука нет; `pending_update_count: 0` при пустой БД — апдейт кем-то получен и подтверждён, но не нашим кодом), сверкой Railway-инфраструктуры (второй проект аккаунта `genuine-rebirth` — голая БД Postgres без бота; `DATABASE_URL` бота и backend идентичны; единственный активный деплой `accurate-expression` на нужном коммите) и чтением кода диспетчера (`bot/bot.py`, `handlers_admin.py` — роутеры подключены верно, перехватывающих `/start` без фильтра обработчиков нет).
- **Устранение:** по решению владельца токен `@Mentalix_club_bot` отозван и перевыпущен через `@BotFather`; обновлён в переменных окружения Railway на обоих сервисах, использовавших старый токен (`accurate-expression` и `mentalix-bot`), оба передеплоены. Повторная read-only проверка Telegram Bot API через ~2 минуты после revoke: старый токен → `401 Unauthorized` на `getMe`/`getUpdates` (revoke применился, но с задержкой — сразу после смены он ещё отвечал `ok:true`); новый токен → `getUpdates` возвращает `{"ok":true,"result":[]}`, конфликта больше нет.
- **Живой тест проведён 12.08.2026 — сидирование по-прежнему не сработало.** После подтверждённого устранения конфликта токена (старый — `401`, новый — чистый `getUpdates`) владелец повторно отправил `/start` с `andre_smi3`. Прямой запрос в БД: 0 строк в `users`. Вывод: конфликт `getUpdates` был реальной проблемой и устранён, но не единственной причиной отсутствия сидирования — есть ещё что-то, разбор не завершён, продолжение в другой раз.
- Код в этой сессии не менялся (ни frontend, ни backend) — только инфраструктура Railway (переменная `BOT_TOKEN`) и внешний токен Telegram. PR не создавался, ветки не заводились.
