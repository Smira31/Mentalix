## P1. Подтвердить ежедневный core loop

Цель: пользователь понимает следующий шаг и возвращается завтра.

```text
check-in → следующий шаг → практика → вечерний разбор → продолжение завтра
```

- проверить первое использование с пустыми ритуалами/аскезами;
- [x] проверить основной сценарий утра и вечера на одном тестовом аккаунте;
- проверить завершение всех типов практик;
- [x] проверить удержание и срыв аскезы;
- [x] проверить переход в AI и обратно;
- определить события продуктовой аналитики;
- измерить completion и next-day return.

Критерий: цикл проходит end-to-end, измеряется и понятен без объяснения автора.

Отбор прошёл через фильтр «тонкое приложение, толстые треки»: ничего ниже не

Порядок — приоритет рассмотрения, не порядок спринтов.

### 1. PIN/биометрия на приложение

**Статус (13.08.2026): закрыто.** PIN-логика и биометрия через
`WebApp.BiometricManager` реализованы (commit `60bd42c`) и обе подтверждены
живым тестом владельца на iPhone в Telegram — настройка через Настройки →
Основные → «Блокировка приложения», холодный старт, возврат из фона, Face
ID/Touch ID. Подробности закрытия — `TASKS.md` → `Completed / Archived` →
`MXL-PIN-001`.

**Что делать.** Опциональная блокировка экрана Mentalix кодом или
биометрией — тумблер в Settings, секция «Основные».

**Механизмы/файлы.** `src/screens/Settings.jsx` — уже есть паттерн `Row` +
`Toggle` внутри `Card`/`SectionLabel`, новый пункт встраивается в секцию
«Основные». Для Telegram — `WebApp.BiometricManager` (Telegram Bot API); для
web-платформы аналогичного API нет, нужен собственный PIN-флоу (модалка +
локальное хранение хэша, по образцу `src/lib/store.js` / `useSynced`).
Потребует нового hook в `src/platform/telegram.hooks.js` по образцу уже
существующих `useMainButton`/`useSecondaryButton`.

**Почему не противоречит принципу.** Не продуктовая фича и не новый трек —
инфраструктурная настройка существующего экрана Settings, защищает то, что
уже есть, а не расширяет поверхность продукта.

**Сложность: S–M.** На Telegram — тонкая обёртка вокруг готового API. На web
придётся написать PIN-флоу с нуля, это поднимает оценку.

### 2. Эмоция → один микро-шаг

**Что делать.** Когда в чек-ине выбрана тяжёлая эмоция (тревожно/подавлен/
страшно из `EMOTIONS[1]`), сразу после шага эмоций предложить один переход —
не меню техник, а один готовый повод написать Собеседнику.

**Механизмы/файлы.** `src/screens/CheckIn.jsx` — шаг эмоций уже есть
(`isEmotionStep`, объект `EMOTIONS`). Handoff-паттерн там же есть как
`openScout()` (sessionStorage `MENTOR_PERSONA_KEY`/`MENTOR_DRAFT_KEY` →
`tab=mentor`), но сейчас жёстко ведёт к персоне `dnevnik` (Следопыт) и
используется только вечером. Нужно обобщить тот же паттерн на персону
`mayak` (Собеседник, см. `src/screens/mentalix/personas.js`) с драфтом,
зависящим от выбранной эмоции, вместо фиксированного `DAY_REVIEW_PROMPT`.

**Почему не противоречит принципу.** Не создаёт тулбокс упражнений под
эмоцию (как у How We Feel) — использует один уже существующий канал
(переход в чат к персоне) вместо форм или списка техник.

**Сложность: S.** Переиспользование существующего механизма, новая логика —
только выбор персоны/драфта по эмоции.

### 3. Дайджест от Следопыта

**Статус (15.08.2026): закрыто.** Реализовано полностью на фронте, backend
не менялся. `deriveConclusions`/`MIN_CHECKINS` экспортированы из
`Analytics.jsx`; новый `src/screens/mentalix/insightDigest.js`
(`maybeBuildInsightMessage`) вставляет находку клиентски перед первым
сообщением при обычном входе в диалог с `dnevnik` — не через
`openScout()`-хендофф. Показ не чаще раза в 4 дня (ключ `mx-insight-seen`,
локально + облако, по образцу `mx-badges-seen` из `Achievements.jsx`),
порог данных — тот же `MIN_CHECKINS` (5 чек-инов), что уже использует сам
«Главный вывод» в «Тренды». Подробности — `TASKS.md`, `CHANGES.md`.

**Что делать.** Периодически (не при каждом открытии) доставлять сильные
находки из аналитики не только графиком в «Тренды», но и репликой от
Следопыта при входе в диалог с ним.

**Механизмы/файлы.** `src/screens/Analytics.jsx` → `deriveConclusions
(checkins, data)` уже считает и ранжирует находки (`{text, weight}`) чисто
на клиенте. Нужен показ «свежей» находки в `src/screens/mentalix/
Conversation.jsx`/`Mentalix.jsx` при открытии персоны `dnevnik`. Паттерн
«показать один раз, не повторять» уже реализован в
`src/screens/Achievements.jsx` (`readSeenEverywhere`/`writeSeen`, ключ
`mx-badges-seen`, синхронизация через `cloud.get`/`cloud.set`) — для
дайджеста нужен аналогичный ключ (например `mx-insight-seen`).

**Почему не противоречит принципу.** Не добавляет отчёт/дашборд (как у
Reflectly) — тот же вывод из той же функции подаётся через уже
существующий канал (реплика AI-персоны) вместо нового UI.

**Сложность: M.** Логика находок готова, но нужно решить, где физически
рождается реплика — на фронте (клиентская вставка перед первым сообщением)
или на бэкенде бота (`mentalix-bot`, отдельный приватный репозиторий — см.
`AGENTS.md`); от этого зависит, потребуется ли согласование
бэкенд-контракта.
