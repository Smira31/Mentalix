# Mentalix — Roadmap v1

Статус: предлагаемый порядок работ. Не является разрешением на продуктовые или визуальные изменения.

## Фактический статус на 29.07.2026

### Verified completed

- production-сборка восстановлена;
- `FORCE_EVENING_REVIEW=false`, вечерний сценарий зависит от `review_hour`;
- smoke-тест пяти вкладок и web auth пройден;
- Telegram fullscreen, safe areas и основной сценарий проверены на iPhone;
- ритуал, аскеза, вечерний анализ, Следопыт и Тренды проверены на одном
  тестовом аккаунте;
- выбор трёх AI-персон, отдельный диалог и ответ Следопыта работают.

### In progress

- системный UI-аудит;
- продуктовые события core loop;
- полировка длинных AI-диалогов и error/retry;
- семидневный тест на 5–10 пользователях.

### Planned

- автоматические тесты, lint и frontend error reporting;
- консолидация архитектуры после P0–P3;
- развитие Пути, аналитики и контента после подтверждения core loop.

### Requires product decision

- финальная палитра;
- архитектура публикации статей;
- роль курсов и тем недели;
- монетизация, entitlement и age/legal решение.

Следующий приоритет: системный UI-аудит без расширения набора функций, затем измеряемый пользовательский тест core loop.

## P0. Стабилизировать текущее состояние

Цель: получить честную baseline-сборку перед экспериментами.

- [x] отключить тестовый вечерний режим: `FORCE_EVENING_REVIEW=false`;
- [x] зафиксировать baseline build;
- [x] провести smoke-тест пяти вкладок;
- [x] проверить Telegram fullscreen/safe areas на реальном iPhone;
- [x] проверить web auth и повторный вход;
- [x] подтвердить основной core loop на одном тестовом аккаунте;
- сверить frontend API с приватным backend.

Критерий: известен результат каждого ключевого сценария и нет тестового режима в production.

## P1. Подтвердить ежедневный core loop

Цель: пользователь понимает следующий шаг и возвращается завтра.

```text
check-in → следующий шаг → практика → вечерний разбор → продолжение завтра
```

- проверить первое использование с пустыми ритуалами/аскезами;
- [x] проверить основной сценарий утра и вечера на одном тестовом аккаунте;
- проверить завершение всех типов практик;
- [x] проверить удержание и срыв аскезы;
- [x] проверить переход в AI и обратно;
- определить события продуктовой аналитики;
- измерить completion и next-day return.

Критерий: цикл проходит end-to-end, измеряется и понятен без объяснения автора.

## P2. Довести AI-сценарии

- три персоны и их различия;
- поле ввода с iPhone keyboard;
- длинный диалог;
- восстановление истории;
- новый journal entry;
- error/retry state;
- безопасные границы ответов.

Критерий: каждая персона проходит сценарий на реальном устройстве без потери текста и истории.

## P3. Наблюдаемость и защита от регрессий

- lint;
- минимальные тесты функций core loop;
- integration-тест API-клиента;
- e2e smoke для критического пути;
- централизованный frontend error reporting;
- чек-лист перед merge.

Критерий: критическая поломка ловится до production или диагностируется по событию, а не по скриншоту пользователя.

## P4. Консолидация архитектуры

Только после P0–P3:

- уменьшить обязанности `App.jsx`;
- формализовать navigation state;
- унифицировать loading/error/empty;
- вынести бизнес-вычисления из крупных экранов;
- определить судьбу legacy `habits`;
- мигрировать legacy design aliases отдельным PR при доказанной пользе.

Критерий: изменение одного сценария не требует несвязанных правок по всему приложению.

## P5. Путь, аналитика и контент

- определить главную метрику Пути;
- не показывать корреляции на недостаточной выборке;
- связать инсайт с конкретным действием;
- выбрать архитектуру статей;
- определить роль курсов и тем недели;
- подготовить хотя бы один законченный авторский трек.

## P6. Монетизация и публичный MVP

Только после подтверждённого core loop:

- решение Telegram Stars/web payment;
- entitlement-модель;
- age/legal решение;
- recovery сценарии оплаты;
- закрытый cohort;
- исправление blocker issues;
- публичный запуск.

## Не делать параллельно

- крупный редизайн и проверку core loop;
- архитектурную миграцию и новую продуктовую функцию;
- смену токенов и исправление mobile behavior;
- монетизацию до подтверждения ежедневной ценности.

## Идеи по итогам конкурентного анализа (Stoic / Reflectly / Daylio / How We Feel) — 2026-08-13

Источник: сравнение Mentalix с Stoic, Reflectly, Daylio и How We Feel (сайты,
App Store/Google Play карточки конкурентов + разбор экранов Mentalix по
исходникам в этой же сессии). Статус: предложение, не разрешение на
реализацию — раздел только фиксирует задачи и их приоритет обсуждения, не
является командой начинать работу.

Отбор прошёл через фильтр «тонкое приложение, толстые треки»: ничего ниже не
добавляет вкладку, новый раздел-каталог или отдельную функциональную
поверхность — каждая задача утолщает уже существующий трек продукта.
Порядок — приоритет рассмотрения, не порядок спринтов.

### 1. PIN/биометрия на приложение

**Статус (13.08.2026): закрыто.** PIN-логика и биометрия через
`WebApp.BiometricManager` реализованы (commit `60bd42c`) и обе подтверждены
живым тестом владельца на iPhone в Telegram — настройка через Настройки →
Основные → «Блокировка приложения», холодный старт, возврат из фона, Face
ID/Touch ID. Подробности закрытия — `TASKS.md` → `Completed / Archived` →
`MXL-PIN-001`.

**Что делать.** Опциональная блокировка экрана Mentalix кодом или
биометрией — тумблер в Settings, секция «Основные».

**Механизмы/файлы.** `src/screens/Settings.jsx` — уже есть паттерн `Row` +
`Toggle` внутри `Card`/`SectionLabel`, новый пункт встраивается в секцию
«Основные». Для Telegram — `WebApp.BiometricManager` (Telegram Bot API); для
web-платформы аналогичного API нет, нужен собственный PIN-флоу (модалка +
локальное хранение хэша, по образцу `src/lib/store.js` / `useSynced`).
Потребует нового hook в `src/platform/telegram.hooks.js` по образцу уже
существующих `useMainButton`/`useSecondaryButton`.

**Почему не противоречит принципу.** Не продуктовая фича и не новый трек —
инфраструктурная настройка существующего экрана Settings, защищает то, что
уже есть, а не расширяет поверхность продукта.

**Сложность: S–M.** На Telegram — тонкая обёртка вокруг готового API. На web
придётся написать PIN-флоу с нуля, это поднимает оценку.

### 2. Эмоция → один микро-шаг

**Что делать.** Когда в чек-ине выбрана тяжёлая эмоция (тревожно/подавлен/
страшно из `EMOTIONS[1]`), сразу после шага эмоций предложить один переход —
не меню техник, а один готовый повод написать Собеседнику.

**Механизмы/файлы.** `src/screens/CheckIn.jsx` — шаг эмоций уже есть
(`isEmotionStep`, объект `EMOTIONS`). Handoff-паттерн там же есть как
`openScout()` (sessionStorage `MENTOR_PERSONA_KEY`/`MENTOR_DRAFT_KEY` →
`tab=mentor`), но сейчас жёстко ведёт к персоне `dnevnik` (Следопыт) и
используется только вечером. Нужно обобщить тот же паттерн на персону
`mayak` (Собеседник, см. `src/screens/mentalix/personas.js`) с драфтом,
зависящим от выбранной эмоции, вместо фиксированного `DAY_REVIEW_PROMPT`.

**Почему не противоречит принципу.** Не создаёт тулбокс упражнений под
эмоцию (как у How We Feel) — использует один уже существующий канал
(переход в чат к персоне) вместо форм или списка техник.

**Сложность: S.** Переиспользование существующего механизма, новая логика —
только выбор персоны/драфта по эмоции.

### 3. Дайджест от Следопыта

**Что делать.** Периодически (не при каждом открытии) доставлять сильные
находки из аналитики не только графиком в «Тренды», но и репликой от
Следопыта при входе в диалог с ним.

**Механизмы/файлы.** `src/screens/Analytics.jsx` → `deriveConclusions
(checkins, data)` уже считает и ранжирует находки (`{text, weight}`) чисто
на клиенте. Нужен показ «свежей» находки в `src/screens/mentalix/
Conversation.jsx`/`Mentalix.jsx` при открытии персоны `dnevnik`. Паттерн
«показать один раз, не повторять» уже реализован в
`src/screens/Achievements.jsx` (`readSeenEverywhere`/`writeSeen`, ключ
`mx-badges-seen`, синхронизация через `cloud.get`/`cloud.set`) — для
дайджеста нужен аналогичный ключ (например `mx-insight-seen`).

**Почему не противоречит принципу.** Не добавляет отчёт/дашборд (как у
Reflectly) — тот же вывод из той же функции подаётся через уже
существующий канал (реплика AI-персоны) вместо нового UI.

**Сложность: M.** Логика находок готова, но нужно решить, где физически
рождается реплика — на фронте (клиентская вставка перед первым сообщением)
или на бэкенде бота (`mentalix-bot`, отдельный приватный репозиторий — см.
`AGENTS.md`); от этого зависит, потребуется ли согласование
бэкенд-контракта.

### 4. «Год пути»

**Что делать.** Компактная годовая/месячная визуализация плотности
чек-инов и практик внутри «Пути»/«Истории» — альтернатива Year in Pixels у
Daylio, но в визуальном языке Mentalix, а не сеткой цветных квадратов.

**Механизмы/файлы.** Переключатель «Путь / История» уже есть в
`src/screens/Today.jsx` (`pathTab`, рендерит `Path` или `History`). Данные —
та же агрегация, что уже собирает `src/screens/History.jsx`
(`api.checkin.history` + `api.analytics.get(...).daily_activity`), только на
более длинном окне. Визуальный язык переиспользуется, а не изобретается
заново: `src/components/Motif.jsx` (`DayArc`, уже в hero Today) и
собственный SVG-инструментарий `src/screens/Path.jsx` (`WireframeMountain`,
`TickGauge`) — оба уже показывают прогресс образом, а не таблицей чисел.

**Почему не противоречит принципу.** Не новый экран и не новая метрика —
другой способ показать те же данные, что уже в «Истории», внутри уже
существующей вкладки.

**Сложность: M–L.** Данные и переключатель вкладок готовы, но сама
визуализация — новый компонент, потребует итераций по читаемости на 30+
точках данных.

### 5. Промпты вместо библиотеки шаблонов

**Что делать.** Вместо отдельного раздела гайд-дневников (как у Stoic) —
ротация авторских вопросов, завязанных на текущую «Тему недели» и тон
активной AI-персоны, подставляемая как плейсхолдер в чек-ине и как
`starters` в чате.

**Механизмы/файлы.** `src/screens/CheckIn.jsx` — плейсхолдер «Начни
писать...» (утро) и `placeholder` в `LESSON_FIELDS` (вечер) сейчас
статичны. `src/screens/mentalix/personas.js` — у каждой персоны уже есть
массив `starters` (тоже статичный, по 2 фразы). `src/screens/
ThemeScreen.jsx` — уже управляет содержанием «Темы недели» (`theme.id`,
`reflected_days`). Нужен источник контента, который вяжет `theme.id` +
`persona.key` + день недели → конкретный текст, и заменяет статику в
перечисленных местах. Готового каталога `src/data/` под такой контент в
проекте пока нет — потребуется завести.

**Почему не противоречит принципу.** Не вводит новый раздел «Гайд-дневники»
— расширяет содержимое уже существующих полей (плейсхолдер чек-ина,
starters чата), давление на структуру продукта нулевое.

**Сложность: M.** Механика подстановки простая, основная стоимость — в
объёме и качестве авторского контента, а не в инженерной задаче.

## Конкурентный анализ: Stoic (08.2026)

**Статус: требует решения владельца, не бэклог.** Раздел фиксирует
наблюдения и идеи-кандидаты по итогам разбора Stoic, не является планом
работ и не добавляет пункты в `TASKS.md` автоматически.

### Наблюдения (стиль и UX)

- Строчные заголовки с точкой в конце ("good afternoon.", "trends.",
  "history.") — тёплый личный тон вместо казённого UI-текста
- Пустые состояния оформлены с пояснением: пунктирный круг-плейсхолдер
  + текст "No data yet — Complete your evening reflections..."
- Единая лента History: check-in'ы, journal-записи и разблокировки
  бейджей идут вместе хронологически, а не по разным разделам
- "Nerdy"-статистика: размер данных, дата первого запуска, число
  апдейтов за год — фан-сервис для вовлечённых пользователей

### Идеи-кандидаты (не решения, требуют отдельного обсуждения с владельцем)

1. Streak-бейджи с именованными уровнями (аналог 10-day streak →
   Youngling → Padawan) — геймификация retention
2. Weekly Theme — недельная сюжетная арка с ежедневным раскрытием
   вопроса (день N из 7, следующие дни закрыты) — пересекается по
   механике с асцезой, нужно решить: замена или дополнение. ВНИМАНИЕ: в
   проекте уже есть экран `src/screens/ThemeScreen.jsx` («Тема недели»),
   на который также опирается пункт 5 «Промпты вместо библиотеки
   шаблонов» из раздела 2026-08-13. Возможно, это одна и та же
   поверхность — уточнить у владельца, прежде чем считать отдельной
   идеей.
3. Единая хронологическая лента истории вместо разделения по типам.
   См. также пункт 4 «Год пути» в разделе 2026-08-13 — тот же экран
   History/«Путь», разные механики (визуализация плотности vs
   объединение типов записей). Смотреть вместе при обсуждении с
   владельцем.
4. Настройка главного экрана — тумблеры, какие карточки показывать
5. Уникальные монохромные иконки под каждый тип ритуала/аскезы —
   ВНИМАНИЕ: может пересекаться с активной задачей MXL-GLYPH-UNIFY-001,
   уточнить у владельца порядок (сначала закрыть unify, потом иконки)
6. Улучшить пустые состояния — добавить пояснение вместо пустого блока
