# Визуальный скачок на финале журнала (журнал: «Сохранить» → финал)

Прогон Chromium (Playwright) в web-контейнере Base44, ветка `journal-reliability`
(база — `f4517dd5`). Вьюпорты задачи — 430×932 (iPhone 15 Pro Max) и 360×640,
демо-режим, `?frame=0` (поверхность считается от размера окна, как на телефоне).

## Причина дефекта (подтверждена замером)

Финал журнала живёт на общей поверхности `<Screen>`, а та брала высоту от
`visualViewport` — контракт `keyboardStrategy: 'resize'` по умолчанию.

`saveAndComplete` показывает финал, как только инсет клавиатуры стал меньше
80 px (`vv.height >= window.innerHeight - 80`), то есть на последнем кадре
анимации закрытия клавиатуры. Поверхность рождается на 60 px ниже
layout-вьюпорта и догоняет его, когда клавиатура закрылась окончательно.
Единственная растягиваемая полоса финала — полоса героя
(`.mx-completion__art-wrap`, `flex: 1 1 auto`; полоса заголовка и нижний блок
не сжимаются), поэтому всю разницу высоты забирает рисунок дневника: он и
меняет размер, и смещается.

**Замер до исправления** (клавиатура: инсет 60 px → 0, тот же кадр, что видит
пользователь в момент открытия финала):

| Метрика | 430×932 | 360×640 |
| --- | --- | --- |
| Высота поверхности (shell) | 872 → 932 px (Δ60) | 580 → 640 px (Δ60) |
| Полоса героя: top / height | 56 / 332 → 56 / 392 px | 56 / 60 → 56 / 120 px |
| **Рисунок: top / height** | **132 / 180 → 162 / 180 px (сдвиг 30 px)** | **56 / 60 → 56 / 120 px (рост вдвое, +60 px)** |
| Заголовок / плашка даты / кнопка «Готово» | 388 / 528 / 800 → 448 / 588 / 860 px (Δ60) | 116 / 252 / 508 → 176 / 312 / 568 px (Δ60) |

## Что изменено

1. `src/components/Screen.jsx` — необязательный проп `keyboardStrategy`
   (по умолчанию `'resize'`, прежнее поведение всех экранов не меняется),
   передаётся в `useFullscreenSurface`.
2. `src/screens/DailyJournal/DailyJournalFlow.jsx` — финал журнала
   (`stage === 'complete'`) открывается на поверхности `'stable'`, как финал
   чек-ина (#1121). Остальные шаги журнала остаются на `'resize'` — там поля
   ввода и клавиатура должна ужимать экран.

Механизм сохранения, черновики, offline-синхронизация, API, тексты и
иллюстрации не тронуты. Общая геометрия демо-рамки, общий scroll-root и
контракт `Screen` по умолчанию не изменены: в демо-рамке (`?demo=1` без
`frame=0`) `top` и `height` поверхности берутся из бокса рамки и при обеих
стратегиях одинаковы.

## Замер после исправления (тот же сценарий)

| Метрика | 430×932 | 360×640 |
| --- | --- | --- |
| Высота поверхности | 932 → 932 px (Δ0) | 640 → 640 px (Δ0) |
| Полоса героя: top / height | 56 / 392 → 56 / 392 px | 56 / 120 → 56 / 120 px |
| Рисунок: top / height | 162 / 180 → 162 / 180 px (Δ0 / Δ0) | 56 / 120 → 56 / 120 px (Δ0 / Δ0) |
| Заголовок / плашка / кнопка | Δ0 / Δ0 / Δ0 | Δ0 / Δ0 / Δ0 |

Рисунок целиком внутри полосы героя (не обрезан), полоса не заходит под кнопку
«Готово», кнопка в пределах экрана, лишнего скролла нет — на обоих вьюпортах.

## Адаптивность при реальном изменении размера экрана

После фикса, закрытая клавиатура: 360×640 → рисунок 120 px (полоса 120),
430×932 → рисунок 180 px (полоса 392, полная высота), возврат к 360×640 →
снова 120 px. Содержимое остаётся доступным, кнопка и рисунок в границах
экрана, скролла нет.

## Ограничения

- Ручной gate iPhone/Telegram (реальная клавиатура, `viewportStableHeight`)
  остаётся за владельцем: в браузере клавиатура имитируется подменой
  `visualViewport.height` (тот же приём, что в `checkin-streak-stability.spec.mjs`).
- WebKit и полный `ux:check` — в CI (по условию задачи локально не запускались).
- Смещения в режиме демо-рамки при прокрутке страницы превью (P1 прежнего
  аудита) не входят в эту задачу: геометрия рамки не менялась.
